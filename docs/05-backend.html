Backend & data

How data outlives a page refresh. The client/server model, relational modelling, the SQL you will actually write, authentication, and the security model that makes it safe for a browser to talk to a database directly.

The client/server model

Your JavaScript runs on someone else's computer, inside a browser you do not control. Anything it can do, a hostile user can do too, by opening DevTools and calling your functions themselves. Therefore:

The only rule that matters

Never trust the client. Every access rule must be enforced somewhere the user cannot edit: a server, or the database itself. Client-side checks are for user experience, not for security.

Three ways to persist data, in increasing order of power:

ApproachGood forLimits
localStoragePreferences, drafts, guest progressOne browser, ~5MB, plain text, user can edit it
Backend-as-a-service (Supabase, Firebase)Real accounts and shared data with no server to runYou must configure its security model correctly
Your own server (Express, Fastify)Custom logic, secrets, third-party integrationsYou operate, secure and scale it

CircuitDojo uses the first two, and deliberately not the third.

Local first

const KEYS = { progress: 'circuitdojo.progress.v1', mastery: 'circuitdojo.mastery.v1', ... };

function read(key, fallback) {
  try {
    const raw = localStorage.getItem(key);
    return raw ? JSON.parse(raw) : fallback;
  } catch {
    return fallback;      // private mode, quota, or corrupt JSON
  }
}
Two habits worth copying

Version your keys (.v1). When the shape changes you can write a migration or ignore the old key instead of crashing on data written by an older build. Wrap it once: no caller should ever have to remember that localStorage throws in private mode or that it stores strings only.

Relational modelling

A relational database stores tables of rows. Design is mostly about answering one question per table: what makes a row unique?

  • Primary key: the column(s) that uniquely identify a row.
  • Foreign key: a column that must point at a real row in another table.
  • Index: a lookup structure that makes a query fast.
  • Normalisation: store each fact once; reference it from everywhere else.

The three tables in this app

create table if not exists public.challenges (
  id                  uuid primary key default gen_random_uuid(),
  template_id         text not null unique,      -- matches the id in code
  topic               text not null,
  difficulty_tier     int  not null check (difficulty_tier between 1 and 8),
  title               text not null,
  brief               jsonb not null default '{}'::jsonb,
  requirements_schema jsonb not null default '{}'::jsonb,
  created_at          timestamptz not null default now()
);
Why a jsonb column instead of more tables

A challenge's requirements are a nested tree of checks whose shape evolves as the engine gains check kinds. Modelling that relationally would need four tables and a join for every read, and every new check kind would need a migration. jsonb is the right call when the data is genuinely document-shaped and only ever read as a whole. Use real columns for anything you filter, sort or join on, which is why topic and difficulty_tier are columns, not JSON fields. 

-- Composite primary key: one row per (user, skill).
create table if not exists public.user_progress (
  user_id  uuid not null references auth.users (id) on delete cascade,
  topic    text not null,
  mastery  numeric(4,3) not null default 0 check (mastery >= 0 and mastery <= 1),
  attempts int not null default 0,
  primary key (user_id, topic)
);

create index if not exists attempts_user_created_idx
  on public.attempts (user_id, created_at desc);

Constraints are documentation the database enforces:

  • not null: this fact is required.
  • check: the range of values that make sense (mastery is a 0-1 fraction).
  • on delete cascade: delete the user, delete their rows. No orphans.
  • unique: no duplicate template ids, ever.
A pragmatic modelling decision from this project

Level tracking needed per-concept mastery after the table already stored per-topic rows. Instead of a migration, concept rows use the same table with a prefixed key: topic = 'concept:ohms_law'. One table, two key spaces, documented in SCHEMA.md. Not textbook-pure, but the alternative was a migration and a second query on every load, for no functional gain.

The SQL you will actually write

-- read
select topic, mastery from user_progress where user_id = '...' order by mastery desc;

-- write
insert into attempts (user_id, result) values ('...', 'pass');

-- write-or-update (idempotent, no read-modify-write race)
insert into user_progress (user_id, topic, mastery) values ('...', 'passives', 0.34)
on conflict (user_id, topic) do update set mastery = excluded.mastery;

-- join
select a.result, c.title
from attempts a join challenges c on c.template_id = a.challenge_template_id
where a.user_id = '...';

-- aggregate
select topic, count(*) as n, avg(mastery) from user_progress group by topic;

Triggers: rules that live with the data

create or replace function public.touch_updated_at()
returns trigger language plpgsql as $$
begin
  new.updated_at = now();
  return new;
end;
$$;

create trigger user_progress_touch before update on public.user_progress
  for each row execute function public.touch_updated_at();

Now updated_at is correct no matter which client wrote the row, including you poking at it in the SQL editor. Rules that must always hold belong as close to the data as possible.

Row Level Security - the important chapter

Supabase exposes your tables over HTTP. Without RLS, anyone with the public anon key could read every row in your database. RLS attaches a rule to each table that Postgres applies to every query, no matter who sends it. 

alter table public.user_progress enable row level security;

create policy "read own progress"
  on public.user_progress for select
  using (auth.uid() = user_id);

create policy "write own progress"
  on public.user_progress for insert
  with check (auth.uid() = user_id);

create policy "update own progress"
  on public.user_progress for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
ClauseApplies toMeans
usingselect, update, deleteWhich existing rows this user may see or touch
with checkinsert, updateWhich rows this user is allowed to create or leave behind

auth.uid() comes from the JWT Supabase attaches to the request. The client cannot forge it: it is signed. So select * from user_progress from a browser returns that user's rows and nothing else, because the database refuses to return anything else.

Two keys, two very different powers

The anon key is public by design and always subject to RLS: shipping it in your bundle is fine and expected. The service role key bypasses RLS entirely. It belongs only in a terminal or a server process, and never in any file that gets committed or bundled.

Read-only reference data gets a policy too, just a permissive one:

create policy "challenges are readable by everyone"
  on public.challenges for select using (true);
-- No insert/update policy exists, so nobody can write it through the API.
-- The sync script uses the service role key from a terminal instead.
A security decision worth understanding

attempts.user_id is nullable, so guest attempts could be stored. There is deliberately no anonymous-insert policy: an anon-writable table with a null owner is an open spam target and buys nothing, because guest progress lives in localStorage until sign-up. If anonymous telemetry were needed later, the right answer is Supabase's anonymous sign-in, which still produces a real auth.uid(): not a relaxed policy.

Authentication

// Current session, plus a subscription to changes (sign-in, sign-out, refresh).
useEffect(() => {
  if (!isSupabaseConfigured) return undefined;
  let cancelled = false;

  supabase.auth.getSession().then(({ data }) => {
    if (!cancelled) setUser(data.session?.user ?? null);
  });

  const { data: sub } = supabase.auth.onAuthStateChange((_event, session) => {
    setUser(session?.user ?? null);
  });

  return () => { cancelled = true; sub.subscription.unsubscribe(); };
}, []);

Sign-up and sign-in are one call each, and both return { data, error } rather than throwing:

const { data, error } = await supabase.auth.signUp({ email, password });
const { data, error } = await supabase.auth.signInWithPassword({ email, password });
await supabase.auth.signOut();
Guest-to-account migration

A user who has already solved ten challenges as a guest must not lose them by creating an account. On successful sign-up, the local snapshot is upserted into the new user's rows. It is twenty lines, and it is the difference between "sign up" being an obvious yes and a risk. 

if (migrateGuestProgress && data.session?.user) {
  const snapshot = localStore.snapshot();
  const rows = [
    ...Object.entries(snapshot.progress).map(([topic, p]) => ({ user_id: ..., topic, mastery: p.mastery, ... })),
    ...Object.entries(snapshot.mastery).map(([id, m]) => ({ user_id: ..., topic: `concept:${id}`, ... })),
  ];
  if (rows.length) await supabase.from('user_progress').upsert(rows, { onConflict: 'user_id,topic' });
}

Query patterns with the Supabase client

// select with filters, ordering and a limit
const { data, error } = await supabase
  .from('attempts')
  .select('id, result, created_at')   // name columns; avoid select('*')
  .eq('user_id', user.id)
  .order('created_at', { ascending: false })
  .limit(50);

// insert
await supabase.from('attempts').insert({ user_id: user.id, result: 'pass', feedback });

// upsert many rows in one round trip
await supabase.from('user_progress').upsert(rows, { onConflict: 'user_id,topic' });
  • Always check error. A failed query returns data null, not an exception.
  • Name your columns. select('*') ships columns you do not need and breaks silently when the table grows.
  • Batch writes. One upsert with ten rows beats ten round trips.

Designing for "no backend configured"

The most-copied idea in this chapter: make the local path a first-class feature rather than an error state. 

if (user && isSupabaseConfigured) {
  await supabase.from('attempts').insert({ ... });
  await supabase.from('user_progress').upsert(rows, { onConflict: 'user_id,topic' });
} else {
  localStore.setProgress(nextProgress);
  localStore.setMastery(nextMastery);
  localStore.addAttempt(attempt);
}

One branch, at the single place that writes. Everything above it: the level model, the UI, the challenge selector: has no idea whether there is a database. That is what makes the feature cheap: the decision is made once, at the edge.

Data-layer checklist

  • Is RLS enabled on every table with user data, with policies for select, insert and update?
  • Does every query check error?
  • Are there indexes on the columns you filter and sort by?
  • Are constraints (not null, check, foreign keys) expressing your invariants?
  • Is the service role key absent from every committed file?
  • Does the app still work with no credentials at all?
  • Is the migration file the source of truth: could you rebuild the database from an empty project?
