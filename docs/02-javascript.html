Chapter 02

JavaScript

You already know what a variable and a loop are. This chapter gives you the JavaScript that professionals actually write, and, more importantly, the reasoning behind each idiom, so you can tell a good pattern from a fashionable one.

Values, and the two that ruin your day

const count   = 42;            // number: one numeric type, no int/float split
const name    = 'R1';           // string
const ok      = true;           // boolean
const nothing = null;           // "deliberately empty"
let   later;                     // undefined, "not set yet"
const parts   = ['R', 'C'];      // array (an object)
const pin     = { num: '1' };    // object

null vs undefined is a real distinction and worth using deliberately: undefined means nobody has supplied a value; null means someone decided there isn't one. CircuitDojo's parseValue() returns null for "this string contains no usable number": a decision, not an accident.

const, let, and never var

  • const: cannot be reassigned. Your default.
  • let: reassignable. Use when a value genuinely changes.
  • var: legacy, function-scoped, hoisted. Never use it.
const is not "immutable"

const doc = { x: 1 }; doc.x = 2; is perfectly legal: you cannot reassign the binding, but the object is still mutable. This trips up everyone once, and it matters enormously in React (see "Immutability" below).

Equality: use === always

'2' == 2      // true , loose equality coerces types. Avoid.
'2' === 2     // false, strict equality. Use this.
null == undefined   // true , the one useful coercion
Object.is(-0, 0)     // false, and this bit us for real
Real bug from this project

A test asserted pin.x % GRID === 0 to check that symbol pins sit on the grid. For x = -30, JavaScript evaluates -30 % 10 as -0, and assert.equal(-0, 0) fails under strict equality. The fix: Math.abs(pin.x % GRID) === 0. Signed zero is not trivia: it is a live edge case.

Truthiness

Falsy values: false, 0, -0, '', null, undefined, NaN. Everything else is truthy, including [] and {}.

if (list.length) { ... }        // idiomatic "not empty"
if (value !== null) { ... }      // explicit when 0 is a valid value

Functions

// Declaration: hoisted, so it can be called before its definition.
function snap(n) { return Math.round(n / GRID) * GRID; }

// Arrow function: concise, and does not have its own `this`.
const snapPoint = (x, y) => ({ x: snap(x), y: snap(y) });

Note the parentheses in => ({ ... }). Without them the braces are read as a function body and you silently return undefined. This is the single most common arrow-function mistake.

Default, rest and spread parameters

// Default value, and an options object with its own defaults,
// the standard way to write a function with optional behaviour.
export function placeComponent(doc, symbolId, unitId, x, y, { rot = 0, mirror = false } = {}) {
  const next = cloneDocument(doc);
  ...
}

// Called with or without the options: both are valid.
placeComponent(doc, 'R', 'A', 10, 20);
placeComponent(doc, 'R', 'A', 10, 20, { rot: 90 });
Why an options object

Positional booleans are unreadable at the call site: place(doc, 'R', 'A', 10, 20, true, false) tells you nothing. Named options are self-documenting and can be extended without breaking existing calls. Use them the moment you have more than one optional parameter.

Closures - the concept that unlocks everything else

A function remembers the variables that were in scope where it was defined.

export function makeRng(seed) {
  let a = (seed >>> 0) || 1;      // private state

  const next = () => {
    a += 0x6d2b79f5;              // the closure can read and update it...
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };

  return { next, int(min, max) { ... }, pick(list) { ... } };
}

Nobody outside can touch a. Two RNGs made from the same seed produce identical sequences, and two made from different seeds never interfere. That is a closure doing the job people reach for classes to do, and it is how every challenge in the app is reproducible from a single number.

Objects and destructuring

const pin = { num: '1', name: 'VCC', x: -60, y: 0, type: 'power_in' };

// Pull fields out by name.
const { name, type } = pin;

// Rename, and supply a default for a missing key.
const { num: pinNumber, len = 10 } = pin;

// Nested, in a parameter list, extremely common in React.
function Pin({ pin: { x, y }, symbol }) { ... }

Spread: copy-with-changes

const moved   = { ...component, x: component.x + 10 };  // object
const appended = [...wires, newWire];                     // array
const merged  = { ...DEFAULTS, ...userSettings };         // later wins
Spread is shallow

{ ...doc } copies the top level only; doc.components is still the same array object. For a genuinely independent copy of nested data, CircuitDojo uses JSON.parse(JSON.stringify(doc)) in cloneDocument(): crude, but honest and correct for plain JSON data, which is exactly what a schematic document is.

Optional chaining and nullish coalescing

challenge?.brief?.spec            // undefined instead of a TypeError
element?.focus?.()                // call only if it exists
const level = template.level ?? template.tier ?? 1;

?? only falls through on null/undefined, unlike || which also rejects 0 and ''. When zero is a legitimate value: a coordinate, a count, a mastery score: || is a bug waiting to happen.

Arrays: think in transformations

Stop writing for loops that push into an array. Describe the transformation instead.

list.map(f)        // same length, each item transformed
list.filter(p)     // shorter, items that match
list.find(p)       // the first match, or undefined
list.some(p)       // boolean: at least one?
list.every(p)      // boolean: all of them?
list.flatMap(f)    // map, then flatten one level
list.reduce(f, x)  // fold everything into one value
list.sort(cmp)     // ⚠ mutates! copy first: [...list].sort()

Real chains from the codebase, and what they say:

// "Which pins on this net are push-pull outputs?"
const drivers = net.pins.filter((p) => p.type === 'output');

// "Name them all for the error message."
drivers.map((d) => `${d.ref} pin ${d.num}`).join(' and ')

// "Every marker point from every failed check, flattened."
evaluation.errors.flatMap((e) => e.points || []).slice(0, 12)

// "How many concepts does this learner hold?"
CONCEPTS.filter((c) => masteryOf(mastery, c.id) >= HOLD).length
Why this reads better

Each line states what is wanted, not how to accumulate it. When you return to this code in six months, filter(p => p.type === 'output') needs no reconstruction in your head, a for loop with an if and a push does.

Map and Set

// Set: fast membership, automatic de-duplication.
const seen = new Set();
seen.add(key); seen.has(key);
[...new Set(refs)]                 // unique list, back to an array

// Map: keyed lookup with any key type, and insertion order preserved.
const BY_ID = new Map(SYMBOLS.map((s) => [s.id, s]));
BY_ID.get('74HC08');

That BY_ID line is the symbol registry. Building the map once turns every later lookup from a linear scan into a constant-time hit, and the netlist extractor does thousands of lookups.

Immutability, and why React demands it

React decides whether to re-render by comparing references. Mutating an object in place leaves the reference identical, so React concludes nothing changed and skips the update. The screen goes stale. 

// ✗ Mutation: React cannot see this.
doc.components.push(component);
setDoc(doc);

// ✓ New objects all the way up the path you changed.
setDoc({ ...doc, components: [...doc.components, component] });

CircuitDojo takes the strictest possible version of this: every editing operation returns a brand-new document. 

export function moveItems(doc, ids, dx, dy) {
  const next = cloneDocument(doc);   // deep copy...
  const sel  = new Set(ids);
  for (const c of next.components) { if (sel.has(c.id)) { c.x += dx; c.y += dy; } }
  return next;                       // ...mutate the copy, return it
}
The payoff

Because no operation ever modifies the document it was given, undo is just "keep the previous one". The entire history feature in this app is a plain array of past documents, no inverse operations, no command pattern, no bugs. Immutability bought a whole feature for free.

Modules

// Exporting
export const GRID = 10;
export function snap(n) { ... }
export default function App() { ... }    // one per file

// Importing
import App, { GRID, snap } from './App.jsx';
import * as edit from './schematic/edit.js';   // namespace
const mod = await import('./heavy.js');            // lazy, at runtime

Each file is its own scope. Two rules worth internalising:

  • Imports are live bindings, not copies. That is why challenges/select.js can import TEMPLATES from challenges/index.js while index.js re-exports from select.js: a circular graph that works because neither uses the other's value until a function is actually called.
  • Import side effects happen once. import './index.css' in main.jsx is not a value import; it tells the bundler "this CSS belongs to the app".
Naming convention used here

Default-export the one thing a file is for (a component, a hook). Named-export everything else. It makes import Palette from './Palette.jsx' unambiguous and keeps utility modules greppable.

Asynchronous JavaScript

JavaScript runs on one thread. Anything slow: a network request, a timer: is handed to the environment and reported back later via the event loop. That is why "wait for this" needs syntax. 

// A Promise is a value that is not ready yet.
const promise = fetch('/api/thing');

// async/await: write it as if it were sequential.
async function load() {
  try {
    const response = await fetch('/api/thing');
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return await response.json();
  } catch (error) {
    console.error('load failed', error);
    return null;                        // degrade, do not crash
  }
}

Two patterns from the codebase worth stealing:

// 1 · Yield to the event loop so the UI can repaint before slow work.
const runCheck = useCallback(async () => {
  setChecking(true);                       // paint "Checking..."
  await new Promise((r) => setTimeout(r, 0)); // let the browser breathe
  const evaluation = evaluateAttempt(schematic.doc, challenge);
  setResult(evaluation);
  setChecking(false);
}, [schematic.doc, challenge]);
Why setTimeout and not requestAnimationFrame

The first version used requestAnimationFrame. In a background tab rAF is throttled to a standstill, so the check appeared to hang forever with the button stuck on "Checking...". A setTimeout(0) yields to the event loop regardless of visibility. Picking the right scheduling primitive is a real engineering decision, not boilerplate. 

// 2 · Guard against a response arriving after the component moved on.
useEffect(() => {
  let cancelled = false;
  (async () => {
    const { data, error } = await supabase.from('user_progress').select('*');
    if (error || cancelled) return;      // stale result, drop it
    setProgress(data);
  })();
  return () => { cancelled = true; };     // cleanup flips the flag
}, [user]);

Classes (and when to skip them)

class UnionFind {
  constructor() { this.parent = new Map(); }

  find(k) {
    let root = k;
    while (this.parent.get(root) !== root) root = this.parent.get(root);
    return root;
  }

  union(a, b) { ... }
}

This is the one class in the whole application, and it earns its place: it is a data structure with invariants and several methods that operate on shared internal state. Everywhere else, plain functions over plain data are simpler to test and impossible to misuse.

Rule of thumb

Reach for a class when you have identity plus behaviour plus invariants. For "transform this data into that data", write a function. Most React codebases contain zero classes, and that is a feature.

Strings, numbers and formatting

// Template literals: interpolation and multi-line, with backticks.
const msg = `${pin.ref} pin ${pin.num} isn't connected`;

// Regular expressions, used here to parse engineering values.
const m = s.match(/^(\d+)\s*([pnuµmkKMGR])\s*(\d+)$/);   // "4k7"

// Numbers: one type, so be careful with money and comparisons.
0.1 + 0.2 === 0.3              // false, floating point
Math.abs(a - b) < 1e-9         // compare with a tolerance instead
(1234.5678).toFixed(2)         // "1234.57" (a string!)
Number('4700')                 // 4700

The value parser is a compact demonstration of string work with a real specification behind it:

// EEs write "4k7" for 4.7kΩ, the multiplier replaces the decimal point so it
// cannot be lost in a photocopy. Parse it once, at the boundary.
const infix = s.match(/^(\d+)\s*([pnuµμmkKMGR])\s*(\d+)$/);
if (infix) {
  const [, whole, prefix, frac] = infix;          // skip index 0
  const n = Number(`${whole}.${frac}`);
  return prefix === 'R' ? n : n * SI_PREFIXES[prefix];
}
Pattern: parse at the boundary

User input is text. Convert it to a number once, as it enters the system, and let everything downstream work in base SI units. The alternative, re-parsing "4k7" in six different places, guarantees six slightly different bugs.

One parser, two formatters

Parsing is a funnel: many spellings, one number, one function. Formatting is not the mirror image of that, and assuming it is caused a whole set of questions to read like typing errors. The same formatValue that correctly writes a resistor as "4.7k" wrote a diode's forward drop as "600m V" and a duty cycle of 0.548 as "548m". 

export function formatReadable(value, unit = '') {
  // "4.4mA" is how an engineer says a current; "0.0044A" is not.
  if (unit) return formatValue(value, unitSymbol(unit));
  // A bare number in a sentence has its unit in the words around it.
  const abs = Math.abs(value);
  if (abs && abs < 1000 && abs >= 0.001) return String(Number(value.toPrecision(3)));
  return formatValue(value, '');
}
Pattern: parsing is one function, presentation is as many as there are contexts

Both of these produce strings the same parser reads back identically, so nothing about correctness is at stake: it is entirely about what a person reads. That is the tell. When two callers want different output from the same value and neither is wrong, you have two presentation concerns wearing one function's name, and the fix is another function rather than a flag on the old one.

Errors and defensive code

export function runCheck(ctx, check) {
  const fn = CHECKS[check.kind];
  if (!fn) return { passed: false, detail: `Unknown check kind "${check.kind}"` };
  try {
    return fn(ctx, check);
  } catch (err) {
    // One malformed check must not take the whole grading run down.
    return { passed: false, detail: `Check failed to evaluate: ${err.message}` };
  }
}
Where to catch

Catch at a boundary where you can still do something sensible. Here, one broken check becomes one failed requirement with an honest message, the learner still gets feedback on the other twelve. Wrapping every individual line in try/catch would just hide bugs.

House style that ages well

  • Name things after what they mean, not their type. netlist, unresolved, claimedCount, not data, arr, temp.
  • Comment the "why", never the "what". // increment i is noise; // -30 % 10 is -0 in JS, so compare the magnitude saves an hour.
  • Keep functions honest about their inputs. Pure in, new value out. Side effects belong at the edges.
  • Small modules with one responsibility. If you cannot name a file's job in five words, it is doing two jobs.
  • Early return over nested if. Handle the impossible cases first, then write the happy path flat.
