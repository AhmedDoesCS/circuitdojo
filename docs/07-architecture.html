Chapter 07

Architecture

How this application is actually put together, and why. Each decision here is transferable: the same shapes solve document editors, level designers, spreadsheet engines and rule-based validators of any kind.

The one decision that mattered most

The engine imports no React. The UI implements no rules. Everything else follows from that.

LayerFolderKnows aboutNever imports
Domain modelsrc/schematic/Symbols, geometry, documents, netlistsReact, DOM
Enginesrc/engine/Electrical rules, requirement checks, hintsReact, DOM
Contentsrc/challenges/Concepts, templates, generation, selectionReact, DOM
Statesrc/state/Hooks that own and persist stateRules, geometry maths
UIsrc/components/Rendering and interactionElectrical rules
What that boundary buys
  • The whole grading engine is testable in Node in ~250ms, with no browser, no rendering library and no mocks.
  • The rules can be reused anywhere: a CLI, a server-side re-check, a batch validator over stored attempts.
  • Bugs are locatable. A wrong verdict is an engine bug; a wrong pixel is a UI bug. You never hunt in both.

The practical discipline: when you feel tempted to put "just a little" domain logic in a component because it is convenient, that is exactly the moment the boundary pays for itself. Push it down.

The pipeline

document (JSON)
   │  extractNetlist()            src/schematic/netlist.js
   ▼
netlist  { nets, pins, components, query helpers }
   │  buildComponentGraph()       src/engine/graph.js
   ▼

   │
   ├─ runERC(doc, netlist, opts)  src/engine/erc.js       → is it a valid circuit?
   └─ runCheck(ctx, check) × N    src/engine/checks.js    → is it the asked-for circuit?
   │
   ▼
result   { passed, correct[], errors[], missing[], warnings[], stats }
   │  generateHints(result, challenge)   src/engine/hints.js
   ▼

Every arrow is a pure function. You can stop at any stage, print the intermediate value, and understand exactly what the next stage sees. That property is worth more than any amount of cleverness inside the stages.

The document model

export function createDocument() {
  return {
    version: DOC_VERSION,
    components: [],   // placed symbol units
    wires: [],        // straight segments between two grid points
    junctions: [],    // explicit connection dots
    labels: [],       // net labels (name a node, supply nothing)
    noConnects: [],   // "this pin is intentionally open"
  };
}

Three properties make this model easy to live with:

  • Flat arrays, not a tree. Every item is reachable without traversal, and the whole document is one JSON.stringify away from the database.
  • Plain data only. No class instances, no functions, no DOM nodes. It survives a round trip through jsonb unchanged.
  • Versioned. version lets a future build migrate old saved documents rather than crash on them.

Coordinates: integers on a grid

/**
 * Everything internal is in "schematic units" where GRID = 10 units = one grid
 * pitch. Every symbol pin sits on a multiple of GRID, and every placement is
 * snapped, so after any 90° rotation or mirror, pins still land exactly on grid
 * intersections. That exactness is what lets net extraction be a plain
 * coordinate-key comparison instead of a fuzzy proximity search.
 */
export const GRID = 10;
export function key(x, y) { return `${Math.round(x)},${Math.round(y)}`; }
Why this is the load-bearing decision of the whole app

Because coordinates are exact integers, "are these two things connected?" is a string comparison. If pins could land on fractional positions, connectivity would need a tolerance, and tolerances need tuning, produce ambiguity, and eventually produce a bug where two things 0.4 units apart are connected on Tuesday and not on Wednesday. The invariant is enforced by a test over the entire symbol library, and that test found two real violations on its first run.

Netlist extraction with union-find

The problem: given a picture of wires, pins and dots, produce the list of electrical nodes. This is a connected components problem, and union-find (disjoint-set) is its standard answer. 

class UnionFind {
  constructor() { this.parent = new Map(); }

  find(k) {                        // which group is k in?
    let root = k;
    while (this.parent.get(root) !== root) root = this.parent.get(root);
    let cur = k;                    // path compression: flatten as we go
    while (this.parent.get(cur) !== root) {
      const next = this.parent.get(cur);
      this.parent.set(cur, root);
      cur = next;
    }
    return root;
  }

  union(a, b) {                    // these two are the same node
    const ra = this.find(a), rb = this.find(b);
    if (ra !== rb) this.parent.set(ra, rb);
  }
}

The algorithm is then a list of rules, each one line:

// (1) Each wire ties its own endpoints together.
for (const w of doc.wires) uf.union(key(w.x1, w.y1), key(w.x2, w.y2));

// (2) Coincident points share a key, so the key IS the identity.
for (const p of pins) uf.add(key(p.x, p.y));

// (3) A junction dot binds a point into the interior of any wire crossing it.
for (const j of doc.junctions) {
  for (const w of doc.wires) {
    if (pointOnSegmentInterior(j, a, b)) { uf.union(jk, key(a.x, a.y)); uf.union(jk, key(b.x, b.y)); }
  }
}

// (4) Power symbols with the same name are one global net, wherever they sit.
// (5) Net labels with the same text are one net, but a label is not a supply.
Modelling a deliberate trap

Two wires crossing without a junction dot are not connected, and the editor never invents a dot for a plain crossing. That is real EDA behaviour and a genuine teachable mistake, so the model preserves it rather than being "helpful". Domain accuracy sometimes means implementing the sharp edge on purpose, and documenting why, or a future contributor will "fix" it.

Give the result a query API, not raw arrays

return {
  nets, pins, components,
  netOfPin(ref, pinNum) { ... },
  groundNets() { return nets.filter((n) => n.isPower && n.powerKind === 'ground'); },
  find(type) { return components.filter((c) => c.symbolId === type || c.tags.includes(type)); },
  // "exclusive" means the net has no other pins, the definition of series.
  sharedNets(refA, refB, { exclusive = false } = {}) { ... },
};

Every rule in the ERC and every requirement check is written against this vocabulary. When the internal representation changes, one file changes. Publishing a vocabulary rather than a data dump is what keeps twenty rule implementations from all depending on your field names.

A second model for a second question

Connectivity cannot answer "is there a DC path from +5V to ground through nothing but a closed switch?" So the engine builds a different graph over the same data: nets are vertices, two-terminal parts are edges, classified by how they conduct. 

/**
 * Edge kinds:
 *   zero     : a closed switch / jumper: a wire for DC purposes
 *   resistive: resistor, pot, thermistor, inductor, unknown external load
 *   diode    : diode / LED: conducts, drops ~0.7-2V, does NOT limit current
 *   clamp    : TVS: off at the working voltage, so no DC path at all
 *   blocking : capacitor: no DC path
 *   active   : transistors, IC internals: not treated as a DC path
 */
export function findPath(adjacency, startNetIds, goalNetIds, allowedKinds) { /* BFS */ }
// "Is a supply tied to ground through nothing but zero-impedance parts?"
const hardShort = findPath(adjacency, supplyNetIds, groundNetIds, ['zero']);
if (hardShort && hardShort.edges.length > 0) { ... }

// "...or through a diode, which cannot limit its own current?"
const diodeShort = findPath(adjacency, supplyNetIds, groundNetIds, ['zero', 'diode']);
Lesson: build a second representation rather than contorting the first

It is tempting to bolt path-finding onto the netlist. Keeping them separate means the netlist stays a faithful description of the drawing while the graph stays a faithful description of conduction. Two small honest models beat one that has to be interpreted differently depending on the caller.

The requirement DSL

Challenges are content, and content should not require code changes. So requirements are data: 

{
  requiredComponents: [{ type: 'D_LED', min: 1, max: 1, label: 'One LED placed' }],
  checks: [
    { kind: 'series', a: { type: 'D_LED' }, b: { type: 'resistor' },
      label: 'Resistor is in series with the LED',
      fail:  'In parallel it does nothing to limit LED current...' },
    { kind: 'value_range', type: 'resistor', inSeriesWith: { type: 'D_LED' },
      min, max, unit: 'Ω', label: 'Resistor sized for 10 mA', fail: 'R = (V − Vf)/I ...' },
  ],
}

The engine is a registry of small pure functions, one per kind:

const CHECKS = {
  series(ctx, check) {
    const as = selectComponents(ctx, check.a);
    const bs = selectComponents(ctx, check.b);
    if (!as.length || !bs.length) return { passed: false, classify: 'missing', detail: ... };
    for (const a of as) for (const b of bs) {
      const shared = ctx.netlist.sharedNets(a.ref, b.ref, { exclusive: true });
      if (shared.length) return { passed: true, detail: ... };
    }
    // Distinguish "touching but not in series" from "not connected at all".
    const touching = as.some((a) => bs.some((b) => ctx.netlist.sharedNets(a.ref, b.ref).length > 0));
    return { passed: false, classify: 'wrong', detail: touching ? 'They do meet, but...' : 'Not connected at all.' };
  },
  value_range(ctx, check) { ... },
  pull_resistor(ctx, check) { ... },
  ...
};

Selectors: a tiny query language

{ type: 'resistor' }                                    // by symbol id or tag
{ type: 'resistor', pin: '1' }                          // a specific pin
{ type: 'resistor', inSeriesWith: { type: 'D_LED' } }    // relational
{ type: 'capacitor', between: [{ type: 'U1', pin: 'VCC' }, { rail: 'ground' }] }
{ rail: 'ground' | 'supply' | '+5V' }                    // a power net
Why go to the trouble of a DSL
  • Content authors write JSON, not code: 36 challenges, zero engine edits.
  • The data can live in a jsonb column and be validated server-side later, unchanged.
  • Each check kind is independently testable and independently fixable.
  • Hints can be generated from the kind, so a new challenge gets guidance for free.

The cost is one indirection. The rule of thumb: build a DSL when you expect many instances of the same shape of rule. Two rules do not justify one; twenty do.

Classify failures, do not just report them

if (result.classify === 'missing') missing.push(entry);   // never addressed
else errors.push(entry);                                // present but wrong

"You never added the decoupling capacitor" and "your capacitor is on the wrong node" require different actions from the learner, so they are different categories in the data model, not just different sentences. Model the distinction your user will act on.

Content generation: templates × seeds

export function instantiate(templateId, seed = randomSeed()) {
  const template = getTemplate(templateId);
  const rng = makeRng(seed);              // deterministic from the seed
  const params = template.params(rng);      // randomise the numbers
  const built = template.build(params);     // hand-authored topology
  return { id: `${templateId}#${seed}`, ...built };
}
Why not generate topologies too

Because a randomly generated circuit is usually nonsense, and occasionally nonsense that looks plausible, which is worse. The split is deliberate: humans author the structure, the machine varies the numbers. You get an effectively unlimited pool where every instance is pedagogically sound. The same principle applies to procedural level design, test-data generation and puzzle games generally.

A challenge instance is (templateId, seed): two small columns that replay an attempt exactly, months later, with no stored copy of the generated content.

Modelling knowledge: provisional vs earned

The level system had a hard product requirement: an experienced user must not be forced through beginner material, and must not be forced to sit a test either. The answer was a state distinction in the data. 

/**
 * Claimed concepts (`self: true`, set by calibration) are treated as held for
 * selection purposes but are *unverified*. The first attempt settles the claim:
 * a pass converts it to earned mastery, a failure drops it well below the hold
 * threshold. That is what makes a wrong self-assessment self-correct in one
 * challenge instead of needing a placement test.
 */
if (passed)          value = Math.min(1, prev.value + (1 - prev.value) * 0.34);
else if (prev.self) value = 0.2;    // a claim that did not survive contact
else               value = Math.max(0, prev.value * 0.7 - 0.05);

Three consequences fall out of that single flag:

  • Placement is one click, because being wrong is cheap and self-correcting.
  • The UI can be honest: the home screen says how many concepts are claimed but unproven.
  • "Too easy: go harder" is trivial to implement: claim the current level, draw from the band above.
Transferable idea

When a system must act on uncertain information, model the uncertainty explicitly rather than pretending the value is known. A boolean beside the number turned a "we need an assessment test" problem into a five-line change.

Overlay state and the single-mount rule

The app has one view variable and a set of overlays. Two rules keep it from tangling:

// 1 · Overlays live ABOVE the view switch, so a transition cannot remount them.
return (
  <div className="relative h-full w-full overflow-hidden">
    {body}                                  /* calibrate | home | workspace */
    {view === 'workspace' && introFor === challenge.id && <ChallengeIntro ... />}
    <ProfileModal ... />
    <IrisTransition run={Boolean(iris)} onMidpoint={applyTransition} ... />
  </div>
);

// 2 · State changes happen at the midpoint of the wipe, while nothing is visible.
const applyTransition = useCallback(() => {
  if (iris.next) { setChallenge(iris.next); schematic.clear(); setIntroFor(iris.next.id); }
  if (iris.toView) setView(iris.toView);
}, [iris, schematic]);
The bug this prevents

In the first version the transition was rendered inside each view branch. Swapping the view at the midpoint unmounted it, a fresh copy mounted with run=true, and the close animation played a second time. The symptom looked like an animation bug; the cause was structural. Anything that must survive a state change belongs above the thing that changes.

And the transition itself is re-entrant-safe, because users double-click:

if (!run) return undefined;
if (busy.current) return undefined;    // already playing, ignore the re-trigger
busy.current = true;

Canvas interaction

Two ideas make the editor tractable:

1 · One transform for the whole scene

<g transform={`translate(${view.x}, ${view.y}) scale(${view.zoom})`}>
  /* everything in world coordinates */
</g>
// Screen → world is then arithmetic, and it is the only place that knows about pixels.
const toWorld = useCallback((event) => {
  const rect = svgRef.current.getBoundingClientRect();
  return {
    x: (event.clientX - rect.left - view.x) / view.zoom,
    y: (event.clientY - rect.top  - view.y) / view.zoom,
  };
}, [view]);

2 · Hit-test the document, not the DOM

export function itemAt(doc, x, y) { ... }        // pure, testable, priority-ordered
export function pinAt(doc, x, y, tolerance) { ... } // pins win over grid when snapping

Wires get a 5px distance tolerance so a 2px line is comfortably clickable; priority is explicit (pins, then labels, then junctions, then wires) rather than an accident of DOM order; and all of it runs in Node under test.

Drag without polluting history

// While dragging, render an offset. Commit ONE move action on drop.
const moveDelta = keyMove ? keyMove.delta : drag?.mode === 'move' ? drag.delta : { x: 0, y: 0 };
<SymbolView component={{ ...c, x: c.x + d.x, y: c.y + d.y }} ... />

Mutating the document on every pointer-move would add sixty undo entries per drag and re-extract the netlist sixty times. Rendering a temporary offset costs nothing and keeps undo meaningful.

Derived state must be re-derived, not accumulated

A junction dot is not a thing the learner owns: most of them are implied by geometry. A pin sitting on the middle of a wire is in that wire, and the dot says so. The tempting implementation is to add a dot when that becomes true. It is wrong, and the bug is invisible: drag the part away again and the dot stays, silently joining two wires that only cross. 

export function normalize(doc) {
  doc.junctions = doc.junctions.filter((j) => !j.auto);  // throw away every derived dot
  // ...then re-derive from the current geometry, leaving hand-placed dots alone
}

Every mutating operation ends with normalize. The rule generalises: if a piece of state is a function of other state, compute it: do not maintain it. Maintaining it means every future operation has to remember to keep it true, and the one that forgets produces a document that lies.

The auto flag is what makes this safe. It separates derived dots from declared ones, so wiping the derived set can never destroy something a person decided.

A preview that disagrees with the commit is a lie

Dragging a component tows the wires attached to its pins. Two pieces of code need to know which wire ends are being towed: the renderer, which draws the stretch, and the edit operation, which performs it. If they compute it separately they will drift, and the failure mode is that you release the mouse and the wire snaps back, having watched it stretch for a second. Both call the same function. 

export function attachmentPoints(doc, ids) { ... } // pins of moving parts + ends of moving wires

Reference answers that are graded before they ship

After three failed checks the app shows the circuit that answers the brief. The audience for that screen is, by definition, someone who cannot tell whether what they are looking at is correct, so it has to be correct by construction, not by review.

The reference is not an image or a description. It is a schematic document of exactly the type the learner draws, built by a small sheet builder, and every one of them is run through the real grader in CI: 

const doc = solutionDoc(challenge);
const result = evaluateAttempt(doc, challenge);
if (!result.passed) failures.push(...);   // across sixteen seeds per template
The test earns its keep twice

It proves the answers are right, and it is a second, independent exercise of the checker, a grader that rejects a correct circuit now fails the build. Content and engine hold each other honest.

What it found the first time it ran

Six new reference answers were written, and three of them refused to pass. Every one was a real defect that made a challenge impossible for anybody to complete:

  • A bulk-capacitor challenge picked its recommended value at random, independently of the droop rule it graded against, so it advised a part twenty times too small and then rejected it.
  • An SPDT level selector reported as a dead short, because the DC graph meshed all three terminals of a changeover switch and believed the wiper could touch both throws at once.
  • A BJT load switch reported its own base as floating, because the brief hands the learner that signal from off-sheet and the ERC had no way to be told so.

None of these were reachable by unit tests of the engine, because each needs a complete, correct circuit to expose it, and the only place a complete correct circuit existed was in the answer nobody had written down yet. Writing the solution is what tests the specification.

What the remaining twenty-four found

Finishing the set, so that every one of the thirty-six templates ships a drawing, produced the same result at a larger scale: three more engine faults and two more challenges nobody could have passed.

  • The ERC compared a pin's name against the supply-or-ground label of the net it landed on, so an op-amp's V− pin correctly wired to a −12V rail was reported as a reversed supply. Comparing voltages instead gets the dual-supply and single-supply cases right for the same reason.
  • The floating-input rule seeded its search from rails only. An inverting amplifier's inverting input reaches no rail at all, only the op-amp's own output through the feedback resistor, and it is nonetheless the most firmly defined node on the sheet. Nets an output drives are sources too.
  • A TVS was classed as an ordinary diode, so every correctly protected supply input looked like a diode short from the rail to ground. A clamp is off at the working voltage by construction, so it is now its own edge kind and never a DC path.
  • Two challenges asked for a strict series pair whose midpoint they also required a pin to reach, which no answer can satisfy at once. Both now state the divider as two halves.
  • Two more counted resistors by tag, and an LDR carries the resistor tag, so four parts counted as five.

A reference drawing is held to a stricter standard than a correct one

Two wires crossing without a junction are not connected. That is true, it is deliberately modelled, and it is exactly the trap the app sets for the learner elsewhere. It also means a reference answer must never do it: the reader of that screen is by definition someone who cannot yet tell a crossing from a connection, so a drawing that relies on the distinction teaches nothing and risks teaching the opposite. 

// No wire may pass over a pin it is not connecting to.
for (const w of doc.wires)
  for (const pin of pins)
    if (onSegmentInterior(pin, w)) offences.push(...);

The rule shapes the drawings. Where three signals fan from one chip to another they stagger their turns to keep the pin order; where a bus needs three things on one net, the sheet uses net labels rather than running one line over another, which is what a real I²C schematic does anyway. Where neither works, a part moves.

Path-level constraints a graph cannot express

The changeover fix is worth stating on its own, because the obvious repair is wrong. Deleting the throw-to-throw edge leaves the graph correct and the answer still wrong: a search can enter one throw, pass through the common terminal and leave by the other, which is the same impossible connection spelled with two edges instead of one. 

// Two edges of the same changeover in one path always means both positions
// at once, because the only way through such a part is via its common pin.
function reusesChangeover(edges, next) {
  if (!next.symbol?.commonPin) return false;
  return edges.some((e) => e.component === next.component);
}

Some constraints belong to the path, not to the edges. When a rule cannot be expressed by adding or removing connections, stop trying to encode it in the graph and put it in the traversal.

The same documents drive the deepest hint. Two schematics of one circuit never match item for item, so the comparison is made on the only things that are the circuit: which kinds of part are present, and which pins share a node. A pin's identity is symbolId.pinName: stable across both sheets, unlike the reference designator. That turns "two things that should be connected are not" into "the LED anode and the resistor are not on the same node on your sheet".

Data-driven parts

{
  id: 'R', name: 'Resistor', refPrefix: 'R', category: 'Passives',
  tags: ['resistor', 'passive', 'two_terminal'],
  defaultValue: '10k', valueUnit: 'Ω',
  units: [{
    id: 'A',
    graphics: [{ t: 'line', pts: [[-20,0], [-16,-7], ...] }],   // zigzag
    pins: [
      { num: '1', name: '~', x: -30, y: 0, orient: 'L', len: 10, type: 'passive' },
      { num: '2', name: '~', x:  30, y: 0, orient: 'R', len: 10, type: 'passive' },
    ],
  }],
}

Symbols are data, and the renderer walks a tiny list of primitives (line, rect, circle, path, text). Adding a part means adding an object, no new component, no new rendering code. The tags array is what lets a challenge say "any resistor" without enumerating every resistor-like part, and type is what the ERC believes about electrical behaviour.

Multi-unit parts, modelled honestly

A 74HC08 is four gate units plus a power unit, all sharing one reference designator. Modelling that faithfully: instead of flattening it to "an AND gate": is what makes "you forgot to place and wire the chip's power unit" a detectable, teachable error. When the domain has a structure, encode the structure; simplifying it away usually deletes the interesting part.

Transferable lessons

  1. Separate pure logic from rendering. It is the difference between a testable system and a pile of components.
  2. Choose a representation that makes features trivial. Immutable documents gave undo away for free.
  3. Publish a vocabulary, not a data dump. Query helpers keep twenty rules from depending on your field names.
  4. Build a second model when a second question appears. Do not contort the first one.
  5. Turn repeated logic into data. Twenty similar rules want a DSL; two do not.
  6. Model uncertainty explicitly. A self: true flag replaced an entire placement-test feature.
  7. Test invariants over the whole dataset. Those tests find bugs that example-based tests never will.
  8. Keep the zero-configuration path working. No credentials, no setup, still runs.
