Chapter 04

Tooling

The machinery around your code: the dev server, the bundler, the styling pipeline, the debugger, the tests and the deploy. Every one of these is a tool you should be able to reason about, not a black box you copy from a starter template.

Why a build step exists at all

Browsers can load ES modules natively, so in principle you need no tooling. In practice you want four things they will not do for you:

  1. Transform code the browser cannot read: JSX is not JavaScript.
  2. Bundle hundreds of module files into a few requests for production.
  3. Optimise: minify, tree-shake unused exports, hash filenames for caching.
  4. Iterate fast: apply an edit without a full reload and without losing state.

Vite

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],           // JSX transform + fast refresh
  server: { port: 5173, open: true },
});

Vite behaves completely differently in the two modes, and knowing that explains most of its behaviour:

npm run devnpm run build
StrategyServes your ES modules directly to the browserBundles everything with Rollup
SpeedInstant start; only the edited file is re-processedSeconds; whole-project optimisation
OutputNothing on diskdist/ with hashed assets

Hot module replacement

When you save, Vite pushes just that module to the browser and React's fast refresh swaps the component while keeping its state. That is why editing a widget does not reset the schematic you were drawing.

When HMR lies to you

If you change the shape of a component's hooks, add a useEffect, reorder useState calls: React cannot reconcile the old instance with the new code and the component can crash or behave oddly. This happened during development of this project and looked like a real bug in the profile modal. Rule: after editing hooks, do a hard reload before you believe a bug.

Environment variables

VITE_SUPABASE_URL=https://xyz.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGci...
const url = import.meta.env?.VITE_SUPABASE_URL;
const anonKey = import.meta.env?.VITE_SUPABASE_ANON_KEY;

// Optional by design: no credentials means guest mode, not a crash at import.
export const isSupabaseConfigured = Boolean(url && anonKey && !url.includes('your-project-ref'));
export const supabase = isSupabaseConfigured ? createClient(url, anonKey, ...) : null;
Only VITE_ variables reach the browser

That prefix is a safety rail: anything without it stays server-side and cannot leak into the bundle. Never put a secret in a VITE_ variable: the bundle is public. The anon key is fine because it is designed to be public and the database enforces access itself (chapter 05).

Design decision: graceful degradation

supabase is null rather than throwing when unconfigured, and every call site checks isSupabaseConfigured. The result: git clone && npm install && npm run dev works on a fresh machine with no accounts, no keys and no setup. Make the zero-configuration path work, and everyone who tries your project succeeds on the first attempt.

Tokens live in the config

export default {
  content: ['./index.html', './src/**/*.{js,jsx}'],   // where to scan
  theme: {
    extend: {
      colors: { zinc: { 150: '#ececee', ... }, good: '#15803d', bad: '#be123c' },
      borderRadius: { widget: '24px', control: '14px' },
      boxShadow: { glass: '0 1px 0 0 rgba(255,255,255,.65) inset, ...' },
      transitionTimingFunction: { smooth: 'cubic-bezier(0.32, 0.72, 0, 1)' },
      keyframes: { irisClose: { ... } },
    },
  },
};
The content array is not optional

Tailwind scans those files as text and emits only the classes it finds. Two consequences: a class built by string concatenation ('text-' + colour) will not exist in the output, and a file outside the glob gets no styles at all. Write complete class names, or map them explicitly.

When to leave Tailwind

@layer components {
  /* A named, reusable surface. Used by ~10 components, so it earns a class. */
  .glass {
    @apply relative rounded-widget border border-white/45 shadow-glass backdrop-blur-2xl;
    background-image: linear-gradient(165deg, rgba(255,255,255,.78), rgba(244,244,245,.58));
  }
  /* The specular highlight needs a pseudo-element: utilities cannot express it. */
  .glass::before { content: ''; position: absolute; inset: 0; background: radial-gradient(...); }
}

Rule of thumb: utilities for one-off layout, a component class when the same combination appears three or more times or when you need something utilities cannot express (pseudo-elements, complex keyframes).

How the bugs in this project were actually found

The iris wipe "not animating" was diagnosed by sampling getComputedStyle(el).clipPath every 120ms during the transition and printing the series. The values never changed, which pointed straight at the CSS variable, not at React. Measure the thing you are unsure about; do not reason about it in the abstract.

Testing

Node has a test runner built in. No Jest, no config, no dependencies.

import { test } from 'node:test';
import assert from 'node:assert/strict';
import { extractNetlist } from '../src/schematic/netlist.js';

test('crossing wires without a junction are separate nets', () => {
  const doc = createDocument();
  wire(doc, 0, 0, 100, 0);
  wire(doc, 50, -50, 50, 50);
  assert.equal(extractNetlist(doc).nets.length, 2, 'a plain crossing must not connect');
});
npm test        # node --test tests/*.test.js
Why this project can test its core so easily

Because engine/ and schematic/ import no React and touch no DOM. Testing the grading logic needs no browser, no rendering library and no mocks: just data in, data out. That is the practical payoff of the architecture in chapter 07, and it is the reason to keep pure logic out of components even when it feels convenient to inline.

Test the invariants, not the implementation

The highest-value suite here is tests/symbols.test.js, which checks properties of the whole library rather than individual behaviour: 

test('every symbol is well formed and on-grid', () => {
  for (const symbol of SYMBOLS) {
    for (const unit of symbol.units) {
      for (const pin of unit.pins) {
        // Note: (-30 % 10) is -0 in JavaScript, so compare the magnitude.
        assert.ok(Math.abs(pin.x % GRID) === 0,
          `${symbol.id} pin ${pin.num}: x=${pin.x} is off-grid`);
      }
    }
  }
});

test('every symbol type and pin referenced by a challenge exists', () => { ... });

These two tests found two genuine bugs on their first run: capacitor pins were off-grid (so wiring to them after a rotation could silently fail) and an H-bridge pin was off-grid. Neither would have been caught by testing a component's rendering.

Assertion messages are the deliverable

assert.ok(cond, 'C.A pin 1: x=-25 is off-grid') tells you the file, the part and the number. A bare assert.ok(cond) tells you a line number. Write the message you would want at 1am.

The dev server's port is part of your data

Browser storage, localStorage, sessionStorage, IndexedDB, cookies: is scoped to the origin, and an origin is scheme + host + port. So http://localhost:5174 is a different website from http://localhost:5173, with its own separate, empty store.

This is a trap during development, because Vite's default is to move out of the way when a port is busy: 

# a stale `npm run dev` is still holding 5173...
Port 5173 is in use, trying another one...
  ➜  Local:   http://localhost:5174/     # ← every saved profile just "vanished"

Nothing was deleted. You are simply looking at a different origin. Turn the silent move off:

server: { port: 5173, strictPort: true }
Prefer a loud failure to a quiet one

"Port 5173 is already in use" looks like the worse outcome and is the better one: it is one stale process away from fixed, and it costs nobody their data. A silent port change costs a user their progress and presents as data loss: you will go looking for the bug in your storage code, where it is not.

Give local-only data a way out

Even on a fixed origin, browser storage is not durable: clearing site data, private windows and storage pressure all take it, and none of them ask. Anything you keep only in the browser should have an export: a JSON download and a matching import is an afternoon's work and it is the difference between a bad day and starting over. Cloud sync is the real answer; a file is the one you can ship before you have accounts.

Git workflow for one person

git switch -c feature/iris-wipe     # branch for a change
# ...work...
git add -A && git commit -m "Fix iris wipe: keyframes, not var transition"
git switch main && git merge feature/iris-wipe
git push

Commit messages that help future-you: say what changed and why it needed to. "Fix bug" is worthless; "Fix iris wipe: CSS vars do not interpolate, use keyframes" is a note to yourself that saves an hour next time.

CircuitDojo itself became a repository on 2 August 2026, later than it should have. The first commit contains the whole app plus a .ui-snapshots/ folder holding all three UI designs the project has had; the second commit deletes that folder. Both designs that are no longer live are therefore still reachable, which is the point of the next section.

Undoing a change

Most git tutorials teach you to save work. The reason you actually save work is to be able to throw some of it away. Four commands cover nearly every "I want yesterday's version back": 

git log --oneline                  # what is undoable, newest first
git reset --hard HEAD              # bin uncommitted edits, back to last commit
git revert HEAD                    # undo the last commit, as a new commit
git checkout HEAD~1 -- src/        # take one folder back a step, leave the rest
CommandWhat it touchesReach for it when
reset --hardUncommitted work onlyAn experiment went nowhere and was never committed
revertAdds a commit that undoes oneA change was committed and you want it gone, with a record that it happened
checkout <ref> -- <path>Just the paths you nameOnly part of a change was wrong: take the UI back, keep the bug fix
reset --hard destroys uncommitted work permanently

It is the one command here with no undo of its own. Anything you have not committed is gone. If you are not sure, commit first: a commit you later revert costs nothing, and a commit you never made costs everything.

Restoring a file must give you the same bytes you had before, and on Windows that is not automatic. Git defaults to core.autocrlf=true, which rewrites line endings when it writes files into your working tree: restore an old version and every line reports as changed. This project ships a .gitattributes containing * -text, which turns that conversion off.

Initialise the repository first, not later

CircuitDojo's UI was rewritten twice and rejected twice before the project had any version control. Getting the earlier design back meant reconstructing it by hand from editor history and backups: an hour of archaeology, dependent on logs nobody had promised to keep, to recover something a single command would have made free.

If you ever find yourself in that position, two things make the reconstruction survivable. Treat the files on disk as the truth and undo later edits backwards from them rather than replaying forward from nothing, except where a file was rewritten wholesale since the date you want, in which case replay forward from its last full write instead, because undoing backwards silently leaves the newer content in place. And check the result: every import should resolve, and files untouched since the target date should already match what is on disk.

All of which is avoidable. git init takes a second, and it is the cheapest insurance in software.

Deployment

npm run build          # → dist/  (static HTML, JS, CSS)
npm run preview        # serve dist/ locally to check it

The output is static files. Any static host serves them: Vercel, Netlify, Cloudflare Pages, GitHub Pages, S3. The whole deploy is:

  1. Connect the git repository to the host.
  2. Build command npm run build, output directory dist.
  3. Set VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY in the host's environment settings.
  4. Push. The host builds and publishes.
Single-page app routing

If you later add client-side routes, the host must serve index.html for unknown paths, or a refresh on /settings returns 404. Every host has a setting for this ("SPA fallback", a _redirects file, or a rewrite rule). CircuitDojo keeps everything on one URL, so it does not need one.

What to check before you call it shipped

  • npm run build succeeds with no warnings you have not read.
  • npm test passes.
  • The production build works from npm run preview, not just in dev.
  • No secrets in the bundle: search dist/ for anything that looks like a key.
  • It works in a fresh private window (no leftover localStorage).
  • Keyboard-only navigation reaches everything important.
  • It behaves with prefers-reduced-motion enabled.
