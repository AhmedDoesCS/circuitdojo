Chapter 03

React

One idea, applied relentlessly: the UI is a function of state. You describe what the screen should look like for the current data; React works out the DOM changes. Everything else in this chapter is a consequence of that idea.

The mental shift

Without a framework you write instructions:

// Imperative: you manage every transition by hand.
button.addEventListener('click', () => {
  count++;
  label.textContent = count;
  if (count > 0) resetButton.style.display = 'block';
});

With React you write a description:

// Declarative: say what is true for this state, every time.
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>{count}</button>
      {count > 0 && <button onClick={() => setCount(0)}>Reset</button>}
    </>
  );
}
Why this scales

The imperative version has a bug the moment a second thing can change count: you must remember to update the label there too. The declarative version cannot have that bug: there is one description, and it is re-evaluated whenever state changes. As a UI grows, the number of possible transitions explodes but the number of descriptions stays at one per component.

JSX

JSX is syntax sugar for function calls. This:

<Widget title="Parts" onClose={hide}>{children}</Widget>

compiles to:

React.createElement(Widget, { title: 'Parts', onClose: hide }, children)

Rules that follow from that:

  • {} escapes into JavaScript. Anything that evaluates to a value can go inside.
  • Attributes are camelCase: className, strokeWidth, onPointerDown, because they are object keys, and class is a reserved word.
  • Components must start with a capital letter, or JSX emits a literal HTML tag instead.
  • Every element must be closed: <br />, <input />.
  • A component returns one root. Use <>...</> (a fragment) when you do not want a wrapper div.

Conditional rendering

{widgets.brief && <BriefWidget ... />}          /* render if true */
{passed ? <Success /> : <Errors />}          /* either/or */
{unresolved > 0 && <Badge n={unresolved} />}  /* note: > 0 */
The zero trap

{count && <X/>} renders a literal 0 on screen when count is zero, because 0 is falsy but still a valid React child. Always compare explicitly: {count > 0 && ...}. CircuitDojo does this for the "unresolved" badge.

Lists and keys

{doc.wires.map((w) => (
  <line key={w.id} x1={w.x1} y1={w.y1} x2={w.x2} y2={w.y2} />
))}

key tells React which item is which between renders so it can move DOM nodes instead of rebuilding them. Use a stable id from your data. Using the array index breaks the moment the list reorders: animations restart, inputs lose focus, and the wrong row appears selected.

Props, and the direction data flows

Props go down; events come back up as callbacks. That is the whole contract.

<BriefWidget
  challenge={challenge}                    /* data down */
  unresolved={unresolved}
  onClose={() => toggleWidget('brief')}    /* events up */
  onTooEasy={goHarder}
/>

Inside, props arrive destructured, with defaults where sensible:

export default function BriefWidget({
  challenge, onClose, onReplayIntro, onBrowse, onNewChallenge, onTooEasy, unresolved = 0,
}) { ... }
Naming convention

Data props are nouns (challenge, mastery); callbacks are on<Thing>. When a child needs something only the app can do: open a panel, run a check, it calls a callback rather than reaching upward. SchematicCanvas takes a single onAppAction('add_component') prop for exactly this reason: the canvas owns the sheet, the app owns the application.

Composition over configuration

// One shell, used by every panel. `children` is the slot.
export default function Widget({ title, subtitle, onClose, actions, children, className = '' }) {
  return (
    <section className={`glass ... ${className}`}>
      <header>
        <h2>{title}</h2>
        {actions}
        {onClose && <button onClick={onClose}><CloseIcon /></button>}
      </header>
      <div>{children}</div>
    </section>
  );
}
Why a shell beats a config object

The alternative is a component with twenty boolean props (hasHeader, showClose, variant...) that becomes unmaintainable. Passing JSX through children and actions means the shell owns appearance and the caller owns content. Every glass panel in this app is visually consistent because of this one file.

useState

const [tool, setTool] = useState('select');        // initial value
const [doc, setDoc]   = useState(() => createDocument()); // lazy init

setTool('wire');                                // replace
setWidgets((prev) => ({ ...prev, brief: !prev.brief })); // derive

Three rules:

  1. Use the updater function when the next value depends on the current one. React batches updates; reading the variable directly can read a stale value.
  2. Pass a function for expensive initial values. useState(createDocument()) calls it on every render; useState(() => createDocument()) calls it once.
  3. Never mutate state. Always produce a new object (chapter 02).

Where state should live

Put state in the lowest component that needs it, and lift it only when a sibling needs it too. CircuitDojo's split:

The most common beginner mistake

Hoisting everything to the top component "just in case". Every state change there re-renders the entire tree. Cursor position lives in the canvas for a reason: at 60 events per second, an app-level re-render would make the editor unusable.

useEffect

Effects synchronise your component with something outside React: event listeners, timers, storage, network, the document title. 

useEffect(() => {
  // 1 · set up
  window.addEventListener('keydown', onKey);
  // 2 · tear down: runs before the next effect and on unmount
  return () => window.removeEventListener('keydown', onKey);
}, [onKey]);   // 3 · dependencies: re-run when these change
DepsRuns

Cleanup is not optional

useEffect(() => {
  if (!run || busy.current) return undefined;
  busy.current = true;

  const at = (ms, fn) => timers.current.push(window.setTimeout(fn, ms));
  at(CLOSE_MS, () => { setPhase('covered'); onMidpoint?.(); });
  at(CLOSE_MS + HOLD_MS, () => setPhase('opening'));

  return () => {
    timers.current.forEach(window.clearTimeout);   // no orphan timers
    timers.current = [];
    busy.current = false;
  };
}, [run]);
StrictMode double-invoke

In development, React 18's <StrictMode> deliberately runs every effect twice: setup, cleanup, setup, to surface missing cleanup. If your effect starts a timer, opens a socket or plays an animation and you see it happen twice, that is not a bug in React; it is React telling you the cleanup is incomplete. Write the cleanup and the double-invoke becomes invisible.

Effects you do not need

// ✗ Derived state in an effect: extra render, easy to desync.
const [total, setTotal] = useState(0);
useEffect(() => { setTotal(items.length); }, [items]);

// ✓ Just compute it.
const total = items.length;

If a value can be calculated from props and state during render, calculate it. Effects are for the outside world, not for bookkeeping.

useMemo and useCallback

// Re-extract the netlist only when the document actually changes,
// not on every mouse move, of which there are ~60 per second.
const netlist = useMemo(() => extractNetlist(doc), [doc]);

const connectedPins = useMemo(() => {
  const set = new Set();
  for (const p of netlist.pins) if (isPinConnected(netlist, p)) set.add(`${p.componentId}:${p.num}`);
  return set;
}, [netlist]);

useMemo caches a value. useCallback caches a function identity, which matters when that function is a dependency of an effect or a prop to a memoised child.

Do not memoise everything

Both hooks cost memory and a comparison. Reach for them when you have measured a problem, or when the work is obviously heavy (parsing a whole document) or the identity is load-bearing (a dependency of an effect). Wrapping every trivial arrow function makes code noisier and slower.

useRef

Two distinct jobs, same hook:

// 1 · A handle on a DOM node.
const svgRef = useRef(null);
<svg ref={svgRef} />
const rect = svgRef.current.getBoundingClientRect();

// 2 · A mutable box that does NOT trigger re-renders.
const cursorRef = useRef({ x: 0, y: 0 });
cursorRef.current = world;        // no render, no stale closure

The second use solves a real problem in this app. The keyboard handler needs the current cursor position to start a keyboard move, but re-creating that handler on every mouse move would be wasteful. A ref gives the handler a live view of a value without making it a dependency. 

case 'move':
  // Attach the selection to the cursor; the next click drops it (KiCad 'M').
  setKeyMove({ origin: { ...cursorRef.current }, ids: selection, delta: { x: 0, y: 0 } });
  break;

useReducer: state with rules

When several pieces of state change together, or a change needs to be describable as an action, a reducer beats a pile of useState. The editor is the textbook case. 

function commit(state, nextDoc, selection = state.selection) {
  if (nextDoc === state.doc) return state;      // nothing changed
  return {
    doc: nextDoc,
    past: [...state.past, state.doc].slice(-HISTORY_LIMIT),
    future: [],                                // a new edit kills the redo branch
    selection,
  };
}

function reducer(state, action) {
  switch (action.type) {
    case 'place': {
      const { doc, component } = edit.placeComponent(state.doc, action.symbolId, ...);
      return commit(state, doc, [component.id]);
    }
    case 'move':   return commit(state, edit.moveItems(state.doc, action.ids, action.dx, action.dy));
    case 'undo': {
      if (!state.past.length) return state;
      return {
        doc: state.past.at(-1),
        past: state.past.slice(0, -1),
        future: [state.doc, ...state.future],
        selection: [],
      };
    }
    default: return state;
  }
}
Why this design is worth copying

Undo/redo is normally a large feature. Here it is fifteen lines, because two decisions cooperate: every edit function is pure and returns a new document (chapter 02), and the reducer keeps arrays of past and future documents. No inverse operations, no command objects. The lesson: pick a data representation that makes the feature trivial rather than writing a clever algorithm around a bad one.

Custom hooks

A custom hook is just a function that calls other hooks. It is how you package stateful logic for reuse.

export default function useSchematic(initialDoc) {
  const [state, dispatch] = useReducer(reducer, initialDoc, initial);

  // A stable API object, so children can depend on it without churn.
  const api = useMemo(() => ({
    place: (symbolId, unitId, x, y, opts = {}) => dispatch({ type: 'place', ... }),
    move:  (ids, dx, dy) => dispatch({ type: 'move', ids, dx, dy }),
    undo:  () => dispatch({ type: 'undo' }),
    ...
  }), []);

  return { doc: state.doc, selection: state.selection, canUndo: state.past.length > 0, ...api };
}

Components now call schematic.move(ids, 10, 0) and never see an action object. The rules of hooks apply: call them at the top level of a component or another hook, never inside a condition or loop, and name them use* so the linter can check you.

Forms and controlled inputs

const [value, setValue] = useState('');

// Re-sync when the selection changes underneath us.
useEffect(() => { setValue(component?.value ?? ''); }, [component?.id, component?.value]);

<input
  data-prop-field="value"              /* so a shortcut can focus it */
  value={value}                       /* React owns the value */
  onChange={(e) => setValue(e.target.value)}
  onBlur={() => commitToDocument(value.trim())}  /* commit on blur */
  onKeyDown={(e) => e.key === 'Enter' && e.currentTarget.blur()}
/>
Why commit on blur, not on change

Typing "4k7" passes through "4", "4k": two of which are invalid or mean something different. Committing on every keystroke would push nonsense into the document and into undo history. Local state while typing, commit on blur or Enter: that is the standard pattern for any field where the value is parsed.

Modals, overlays and the mount trap

A component that renders null when closed is still mounted. Its state persists. This bit this project for real: 

export default function ProfileModal({ open, initialTab = 'progress', ... }) {
  const [tab, setTab] = useState(initialTab);

  // The component stays mounted and renders null when closed, so useState's
  // initial value would stick forever. Re-sync on every open instead, or the
  // "?" shortcut would land on whichever tab was opened first.
  useEffect(() => { if (open) setTab(initialTab); }, [open, initialTab]);

  if (!open) return null;
  ...
}

Two ways out: sync with an effect (above), or force a remount with a changing key (<Modal key={openCount} />). Both are legitimate; the effect is cheaper.

Single-mount rule for transitions

The iris wipe swaps the app's view at its midpoint. In the first version the transition component was rendered inside each view branch, so switching view unmounted it and a fresh copy replayed the close: a visible double-play. The fix was structural: render the transition once, above the view switch. Anything that must survive a state change belongs above the thing that changes.

Events, and why this app hit-tests itself

<svg
  onPointerDown={handlePointerDown}
  onPointerMove={handlePointerMove}
  onPointerUp={handlePointerUp}
  onContextMenu={(e) => e.preventDefault()}
/>

Note there are no handlers on the individual wires or symbols. All three handlers live on the <svg>, and the code works out what was hit by comparing world coordinates against the document: 

export function itemAt(doc, x, y) {
  for (let i = doc.components.length - 1; i >= 0; i--) {   // topmost first
    if (hitComponent(doc.components[i], x, y)) return { kind: 'component', item: doc.components[i] };
  }
  for (const w of doc.wires) {
    if (distanceToSegment({ x, y }, ...) < 5) return { kind: 'wire', item: w };
  }
  return null;
}
Why not per-element handlers

Three reasons. A 2px wire is nearly impossible to click, but a 5px distance tolerance is comfortable. Hit priority becomes explicit, pins beat bodies beat wires, instead of depending on DOM order. And the logic is pure, so it is unit-testable without a browser. The cost is that you write the maths yourself; for a drawing tool that is the right trade every time.

Performance in practice

  • Keep fast-changing state local. Cursor position never leaves the canvas.
  • Memoise derived work, not everything. The netlist is memoised on [doc].
  • Render from data, not from imperative updates. Dragging renders a transform offset; the document is only rewritten on drop, which also keeps undo history clean.
  • Animate transform, opacity and clip-path: the compositor can do those without layout.
  • Measure before optimising. DevTools' Performance panel tells you the truth; intuition does not.

Component review checklist

  • Does it own only state that nothing else needs?
  • Is every list keyed by a stable id?
  • Does every effect have correct dependencies and a cleanup?
  • Are conditionals explicit (> 0, !== null) rather than truthy?
  • Do callbacks flow up rather than the child reaching into global state?
  • Is state replaced, never mutated?
  • If it renders null when closed, is its internal state re-synced on open?
