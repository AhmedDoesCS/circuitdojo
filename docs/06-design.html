Chapter 06

Design

The chapter that turns "it works" into "someone with taste made this". Design is not decoration you add at the end: it is a set of decisions with reasons, and reasons can be taught. Everything here is a rule you can apply tomorrow, with the code that implements it.

A note on this chapter's history

CircuitDojo went through three whole-cloth UI rewrites: a translucent "Liquid Glass" one, a ground-up rebuild, and a dark "Signal" language, and each was abandoned. The app was restored to the first, and has since been changed a decision at a time: a type system, then themes and accents, then the flat surfaces described below. Those stuck.

That is the lesson, and it is worth more than the pixels. A redesign is not obviously an improvement. Each rewrite was coherent on its own terms and still landed further from what the project wanted, because a rewrite changes a hundred things at once and gives you no way to tell which one you disliked. Changing one axis at a time is slower to describe and far faster to converge. Either way, keep the old version recoverable before you start: every design in this project's history is still one git show away.

What "designed" actually means

Award-winning interfaces are almost never more decorated than amateur ones. They are more decided. Four things separate them:

PropertyAmateurDesigned
HierarchyEverything competes for attentionOne clear focus per screen; everything else recedes
ConsistencyNine spacing values, six greys, four radiiA small system, reused without exception
RestraintColour, shadows and animation everywhereNeutral by default; emphasis is rationed and therefore means something
Intent"It looked nice"Every choice has a one-sentence reason
The test to apply to your own work

Point at any element and ask: why is it that size, that colour, that far from its neighbour? If the answer is "it looked about right", that is where your design is weak. If it is "it is step 2 on the type scale because it is secondary to the title", you are designing.

Typography

Type does most of the work. Get this right and a plain layout already looks professional.

Choosing a typeface

Two faces, each with one job. More than two and the page stops having a voice; fewer and you cannot separate a measurement from a sentence.

FaceJobNever
InterAll UI and prose: buttons, labels, headings, body copyValues or pin names
JetBrains MonoAnything measured or typed: resistances, reference designators, pin numbers, keyboard hints, schematic labelsProse, ever
fontFamily: {
  sans: ['Inter', '-apple-system', 'BlinkMacSystemFont', '"Segoe UI"', 'system-ui', 'sans-serif'],
  mono: ['"JetBrains Mono"', 'ui-monospace', 'SFMono-Regular', 'Menlo', 'monospace'],
}

Inter is the house style of modern software for a reason: it is a neutral grotesque drawn for screens, it stays legible at 11px, and it tightens up cleanly at display sizes. Picking it is not a bold choice, and that is the point: the typeface should not be the thing anyone notices.

Keep the system stack behind the webfont

The fallbacks after Inter are not decoration. With display=swap, the app renders immediately in the system face and upgrades when the webfont lands, so a slow or absent network costs you nothing but the exact letterforms. A font the user has to wait for is a font that breaks your first impression.

Route every mono through the config, including SVG

Schematic labels are drawn as SVG <text>, and it is tempting to set fontFamily="ui-monospace, monospace" right on the element. Do not: change the project's mono later and those labels silently keep the old one, so the sheet and the panels drift apart. Give the element className="font-mono" instead and let the Tailwind config stay the single source of truth.

Use a scale, not arbitrary numbers

Pick a ratio (1.2 for dense UI, 1.25 for general, 1.333 for editorial) and step through it:

:root {
  /* 1.25 ratio, fluid: min at small screens, max at large, no media query. */
  --step--1: clamp(0.78rem, 0.76rem + 0.1vw, 0.83rem);
  --step-0:  clamp(0.94rem, 0.9rem  + 0.15vw, 1rem);
  --step-1:  clamp(1.1rem,  1rem    + 0.4vw,  1.3rem);
  --step-2:  clamp(1.35rem, 1.15rem + 0.8vw,  1.85rem);
  --step-3:  clamp(1.7rem,  1.3rem  + 1.6vw,  2.6rem);
  --step-4:  clamp(2.1rem,  1.4rem  + 3vw,    3.8rem);
}

clamp(min, preferred, max) is the single most useful function in modern CSS layout:

  • It scales with the viewport, so one value covers laptop to 4K.
  • It has hard limits, so text never becomes unreadable or absurd.
  • It removes whole categories of media query.

In the app, the same idea appears inline where a component needs it:

<span
  className="block font-semibold tracking-[-0.02em]"
  style={{ fontSize: primary ? 'clamp(1.5rem, 3.1vw, 2.5rem)' : 'clamp(1.15rem, 2.1vw, 1.7rem)' }}
>
  {label}
</span>

Tracking: tighten as size grows

h1 { letter-spacing: -0.035em; }   /* large: tighten hard */
h2 { letter-spacing: -0.025em; }
body { letter-spacing: 0; }         /* body: leave it alone */
.eyebrow { letter-spacing: 0.1em; }  /* small caps: open it up */
Why negative tracking on headings reads as "designed"

Type designers space fonts for body text. At 48px those gaps look loose and amateurish. Every carefully-made marketing site tightens display type: it is one of the highest-impact single lines of CSS you can write. Conversely, uppercase micro-labels need more space or they turn into a smear.

Line height and measure

  • Body: 1.6-1.7. This manual uses 1.68.
  • Headings: 1.0-1.15. Big type needs less.
  • Measure (line length): 45-75 characters. max-width: 76ch here; max-w-[46ch] on the app's intro paragraphs.

Two or three weights, maximum. This project uses 600/650 for headings and 400/500 for text, and no italics except for pull-quotes.

Space

Spacing is where amateur work is most obviously amateur, and it is the easiest thing to fix.

One rhythm, everywhere

:root {
  --s1: 0.25rem;  --s2: 0.5rem;  --s3: 0.75rem;  --s4: 1rem;
  --s5: 1.5rem;   --s6: 2rem;   --s7: 3rem;     --s8: 4.5rem;
}

Tailwind gives you this for free: its scale is 4px-based. The discipline is to only use the scale. The moment you write margin-top: 13px, you have started a second system.

Proximity communicates grouping

Related things sit close; unrelated things sit far apart. If a label is equally distant from the field above and the field below, the reader cannot tell which it belongs to. Halve the inner gap and double the outer one and the layout explains itself with no lines or boxes.

Whitespace is the luxury signal

// The safe area scales with the viewport: never cramped, never lost.
<div
  className="relative z-10 flex h-full w-full flex-col justify-center"
  style={{
    paddingInline: 'clamp(2.5rem, 8vw, 10rem)',
    paddingBlock:  'clamp(2rem, 7vh, 5.5rem)',
  }}
>
Why the home screen's margins got much larger

The first version used a fixed px-6. It read as a website: content pinned near the edges, header at the top, an implied scroll. Games and native apps put their menus in the middle of a large calm field, because generous margins say "this space is mine to use, not a document to be consumed". Two clamp() values changed the entire character of the screen without touching a single component inside it.

Colour

The structure that almost never fails:

  1. One neutral ramp (8-10 steps) for 90% of the interface.
  2. One accent, used sparingly for the primary action.
  3. Three semantic hues: success, warning, danger, used only for meaning.
  4. Optionally one signature colour tied to the subject matter.
colors: {
  zinc: { 25: '#fcfcfd', 50: '#fafafa', 100: '#f4f4f5', 150: '#ececee', ..., 900: '#18181b' },
  accent: { DEFAULT: '#3f3f46', soft: '#71717a', deep: '#27272a', tint: '#2563eb' },
  good: '#15803d', warn: '#b45309', bad: '#be123c',
  // The subject's own palette: KiCad conventions. This is the signature.
  sch: { body: '#8b1a1a', bodyFill: '#fff8e6', wire: '#0f7a3d', label: '#0d6e6e' },
}
Why the chrome is neutral and the accent is a dark grey

The schematic sheet is the subject, and it is already coloured: maroon symbols, green wires, teal labels. A blue accent in the surrounding UI would compete with it. So the interface is zinc, the primary button is near-black, and the only saturated colour in the chrome is status: red for unresolved, amber for missing, green for verified. Colour that always means something is colour the user learns to trust.

Theming: invert the ramp, do not rewrite the app

The obvious way to add a dark mode is to replace every zinc-900 with a semantic name like text-primary and define both themes behind it. That is a thousand edits, and every one is a chance to change something you did not mean to.

There is a cheaper route, and it is available whenever a codebase has used its neutral scale consistently: in CircuitDojo, zinc-900 always means ink, zinc-200 always means the page, zinc-900/[0.06] always means a faintly raised surface. When that holds, the dark theme is the same ramp read backwards: 

:root {
  --zinc-200: 228 228 231;  /* the page  */
  --zinc-900: 24 24 27;     /* the ink   */
}
[data-theme='dark'] {
  --zinc-200: 18 18 21;     /* ...swap the ends */
  --zinc-900: 244 244 245;
}
zinc: { 900: 'rgb(var(--zinc-900) / <alpha-value>)', /* ... */ }

<alpha-value> is the part that makes this practical: Tailwind substitutes the opacity into the rgb() at build time, so bg-zinc-900/[0.06] keeps working untouched. Every existing class flips on its own and no component learns that a theme exists.

Three things an inverted ramp cannot express

Text on a solid surface. bg-zinc-900 flips to near-white, so a hardcoded text-white label on it disappears. Those need their own token, here --on-solid, white in light and near-black in dark.

Glass and shadow. These change alpha as well as hue: 78% white frosting reads as a pane on a light ground and as a glare on a dark one. Store them as complete colour values, not triplets the opacity utilities can re-derive.

Anything outside the neutral system. Status colours and the schematic palette have to be lifted by hand: a green chosen to carry on white is too dark on near-black.

Ship the new theme as a no-op

The default here stays light with the neutral accent, and it renders byte-identical to the version before theming existed: same page rgb(228,228,231), same ink, same glass gradient. A theming change that alters the default look is two changes wearing one coat, and when someone dislikes the result you cannot tell which half they mean.

Never pure black, never pure white

#000 on #fff is harsh and looks unconsidered. #18181b on #ececee is softer, has a subtle temperature, and gives you room to place true white as a highlight.

Opacity over new colours

// One colour, many weights, automatically coherent on any background.
"bg-zinc-900/[0.04]"   // subtle fill
"bg-zinc-900/[0.06]"   // hover
"border-black/[0.06]"  // hairline
"bg-bad/10"            // danger tint behind red text

Depth and material: flat surfaces

There are two honest ways to say "this element is in front of that one". You can imitate a material: give the panel thickness, a lit edge, and something to refract, which is what translucent glass does. Or you can change its tone and let a soft shadow do the separating. CircuitDojo used the first and now uses the second. 

.panel {
  @apply rounded-widget;
  background-color: rgb(var(--panel));   /* one solid tone   */
  box-shadow: var(--elev-1);           /* one soft shadow  */
}

That is the whole recipe. No gradient, no border, no backdrop filter, no specular inset: four things removed, and the panel still reads as a panel.

Doing the workReads asGet it wrong and...
Tone against the groundA distinct surfaceThe panel dissolves into the page
A soft, low-contrast shadowSitting slightly aboveHeavy shadow: dated, 2013-skeuomorphic
Radius, held to a small scaleDeliberate, engineeredToo round reads toylike; square reads unfinished
A filled accent on one controlWhere to clickAccent everywhere: nothing is primary

Elevation is tonal, and it inverts

On a light ground, a raised surface is lighter than the page and casts a shadow. On a dark ground the shadow has nothing left to darken, so elevation has to come from tone alone: a raised surface gets lighter there too, which is the opposite of what "shadow = depth" would predict: 

:root              { --panel: 255 255 255; }  /* above a #e4e4e7 page */
[data-theme='dark'] { --panel: 28 28 32; }     /* above a #121215 page */

Three steps are plenty: the page, the panel, and a recessed tone inside it for tab strips, filled fields and key caps. If you find yourself wanting a fourth, the layout is probably nested too deep.

Radius: a scale, not a vibe

Pick four values tied to component size and never improvise a fifth. Large radii age badly: 24px on a panel starts to read as a capsule, and capsules were the house style of a specific era. 

borderRadius: {
  widget:  '16px',  /* panels, cards, modals          */
  bar:     '14px',  /* toolbars, the switchboard      */
  control: '10px',  /* buttons, fields, list rows     */
  chip:    '8px',   /* chips, tags, key caps          */
}
Keep circles where the shape means something

Going flatter is not a reason to square off a progress track, a status dot, an avatar or a toggle knob. Those are round because the shape carries the meaning, not because of a style. The rule worth holding is narrower: chrome stops being capsule-shaped, geometry does not.

What removing the glass actually costs

Two real things. Translucency told you the canvas continued underneath a floating panel; opaque panels do not, so the panel has to earn its screen space instead. And blur gave separation for free on any background, whereas tone has to be chosen per theme: a surface that reads as raised on white will read as a hole on near-black.

What it buys: backdrop-filter is the most expensive property on the page, because the compositor has to sample and blur everything behind the element on every frame. Dropping it removes that cost from every panel at once.

Backgrounds: draw the thing, do not blur a colour

The default way to make a background "interesting" is two or three big blurred colour blobs drifting behind the content. It is one CSS rule and it works on any site, which is exactly the problem: it belongs to no particular product, and it is the single least flat thing you can put on a screen. Three of them were what sat behind CircuitDojo's menus.

The replacement is a drawing of the subject: a printed circuit board. Same job: low-contrast texture that gives the screen depth without competing, but it now says what the app is about. Getting it to read as a real board rather than a generic circuit motif came down to four details:

DetailWhy a real board has it
45° corners on every traceEtchant undercuts an acute angle and the corner traps flux, so copper is never routed at a sharp 90°. This is the single strongest tell.
Vias as rings, not dotsA via is a plated hole. Drawn as a stroked circle, the barrel reads as hollow.
Footprints, not schematic symbolsA board shows pads and silkscreen outlines. Putting a resistor zigzag on a PCB is a category error: that is the drawing of the board, not the board.
Hatched copper pourHow a ground region is rendered on a fabrication plot.

The routing is generated rather than hand-drawn: waypoints go in, and a route() helper mitres every corner by cutting both legs back and joining the cut points. Fifteen lines, and it is what stops the traces looking hand-placed.

Canvas cannot inherit your theme

SVG reads var(--token) in a presentation attribute, so themed artwork is free. A <canvas> cannot: you have to sample the values with getComputedStyle(document.documentElement) when you draw. Miss that and the celebration confetti keeps firing light-mode maroon over a near-black screen, where half of it never shows up.

Flat is not featureless

"Remove the gradients" is easy to over-apply until every surface is the same tone and the hierarchy is gone. Flat design leans harder on the things that remain: tone steps, spacing, type weight and one saturated accent, not on fewer of them. If a flat screen looks bland, the fix is usually more contrast between the surface tones, not the gradient back.

Motion

Motion has exactly three legitimate jobs: show where something came from, show what changed, and cover a state change you do not want witnessed. Anything else is decoration that costs the user time.

Duration and easing

InteractionDurationEasing
Hover, focus, small state150-200msease or a gentle custom curve
Panel enter/exit250-320msDecelerate: cubic-bezier(0.32, 0.72, 0, 1)
Full-screen transition500-700msSame decelerate curve
Celebration700ms+, with a springcubic-bezier(0.34, 1.56, 0.64, 1)
transitionTimingFunction: {
  // Fast out, long gentle settle. Reads as "physical" rather than "linear".
  smooth: 'cubic-bezier(0.32, 0.72, 0, 1)',
  spring: 'cubic-bezier(0.34, 1.4, 0.64, 1)',   // slight overshoot
}

One curve, used everywhere, is a large part of why an interface feels like one product. Two random easings look like two teams.

Entrances: move a little, not a lot

keyframes: {
  widgetIn: {
    '0%':   { opacity: '0', transform: 'translateY(10px) scale(0.97)' },
    '100%': { opacity: '1', transform: 'translateY(0) scale(1)' },
  },
}

10px and 3% scale. Enough to register as arriving, small enough that it never delays comprehension. Beginners animate 60px and 0.8 scale, which reads as a cartoon.

Stagger to imply structure

Elements arriving one after another in reading order teach the reading order, without any explicit cue. The trap is doing it ad hoc: pick a delay per element by eye and within a few edits they drift out of sequence: on this screen the objectives card was arriving before the sentence that introduces it, because the two numbers were chosen weeks apart.

Give the screen one beat and count in it:

const LEAD_IN = 0.2;   /* wait for the cover to start lifting */
const BEAT = 0.05;
const at = (step) => ({ animationDelay: `${(LEAD_IN + step * BEAT).toFixed(3)}s` });

// ...then position each element on the beat, in reading order.
<h1 style={{ ...at(1) }}>            /* headline    */
<p  style={at(1.5)}>               /* the tagline */
<PrimaryAction delay={at(2.5)} />  /* the action  */

Fractional steps are the reason this holds up: a stack of three rows can be tightened to half a beat each without inventing a second timing system, and the whole ladder stays sortable and reviewable. Reordering the screen means renumbering, not re-guessing.

Direction carries meaning too. On the home screen the hero column rises from below while the save-file panel slides in from the side, so the two columns do not arrive as one block, and the eye is given the thing you came for first.

Keep total stagger under ~400ms of delay. Beyond that the last item feels late and the user has already started reading it. This screen's ladder runs 200ms to 600ms across fourteen elements, and the last one is a keyboard hint nobody is waiting on.

An entrance nobody sees is not an entrance

The first version of this cascade was tuned in isolation and looked right in isolation. In the app it was invisible, because of when it ran rather than how fast.

A screen arriving through a transition mounts while the transition is still covering it. Here the incoming screen mounts at the iris wipe's midpoint, and the cover then holds and opens on its own schedule, so the clock the animation starts on is not the clock the viewer is watching:

ms after the screen mountsWhat the viewer seesWhat the entrance is doing
0Fully coveredCascade begins
140Cover starts to liftHalf done
700Fully revealedLong finished: the screen is simply there

Speeding the animation up made it worse, and slowing it down only partly helped. The fix is a lead-in: hold the first element back until the cover has begun to move, so the cascade plays in front of the viewer rather than behind a curtain. Keep it shorter than the full reveal: the elements should be arriving as the screen opens, not waiting politely for it to finish.

Tune motion against the whole sequence, not the component

Any animation that plays on mount has this problem the moment it lives behind a route transition, a modal or a skeleton. Before adjusting a duration, work out what is on screen while it runs. The question is almost never "is this too fast": it is "is anyone looking yet".

The iris wipe: a full case study

The goal. Cover the screen so the challenge swap is never witnessed, then reveal the new one.

/* Note the direction of the clip: this element is the *cover*, so a large
   circle means "screen hidden" and a zero circle means "screen visible".
   Closing the iris therefore GROWS the circle. */
.iris {
  position: fixed; inset: 0; z-index: 120;
  pointer-events: auto;          /* swallow clicks while playing */
  background: radial-gradient(circle at center, #fbfaf7 0%, #e4e4e7 100%);
  clip-path: circle(0% at 50% 50%);
  will-change: clip-path;
}

@keyframes irisClose { from { clip-path: circle(0% at 50% 50%); } to { clip-path: circle(150% at 50% 50%); } }
@keyframes irisOpen  { from { clip-path: circle(150% at 50% 50%); } to { clip-path: circle(0% at 50% 50%); } }

.iris-closing { animation: irisClose 700ms cubic-bezier(0.32,0.72,0,1) forwards; }
.iris-covered { clip-path: circle(150% at 50% 50%); }
.iris-opening { animation: irisOpen  700ms cubic-bezier(0.32,0.72,0,1) forwards; }

Three bugs this went through, and the lesson from each:

  1. It did not animate. The first version transitioned clip-path: circle(var(--iris)). A var-substituted value does not interpolate, so it jumped to the end state. Lesson: animatable does not mean animatable through a variable. Use keyframes with literal values.
  2. It played twice. The component was rendered inside each view branch, so swapping the view at the midpoint unmounted it and a fresh copy replayed the close. Lesson: anything that must survive a state change belongs above the thing that changes.
  3. The clip was inverted. "Closing" shrank the circle, which actually uncovers. Lesson: write the direction of a mask in a comment. It is not obvious and you will get it wrong twice.

Pacing. 700ms in, 260ms held, 700ms out.

Why not faster

Below ~400ms a full-screen wipe reads as a flicker rather than a scene change, and the moment of stillness that makes it feel intentional disappears. Above ~900ms per half you are making the user wait. The 260ms hold exists because a cover with no pause looks like a glitch: the eye needs a beat to register that the screen changed on purpose.

Respect the user's setting

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
// JS-side too: skip straight to the state change, no timers at all.
const reduced = window.matchMedia?.('(prefers-reduced-motion: reduce)').matches;
if (reduced) { onMidpoint?.(); onComplete?.(); return; }

Everyone gets the information; only the motion is optional. This is both an accessibility requirement and a design constraint that improves the work: if your interface only makes sense with the animation, the layout is not doing its job.

Composition: designing a game menu

The brief for CircuitDojo's home screen was "less website, more game". Concretely, that is five decisions:

1 · Lock the viewport

fixed inset-0 overflow-hidden. A menu that scrolls is a document. If it does not fit, the layout is wrong: do not add a scrollbar.

2 · Centre in a large field

Vertically centred content with clamp() margins. Websites stack from the top; apps sit in the middle of their space.

3 · One dominant action

A single oversized action, with the rest stacked beneath it at two-thirds the weight and sharing its width. A menu with six equal options has no primary, and does not fit.

4 · A status panel

The "save file": level, progress, stats. Games always show you where you are before you press start.

5 · Ambient life

A drawn background at very low contrast, with one slow loop in it. Presence without demand, and drawn, never blurred.

6 · Keyboard first

↑ ↓ ← → to move, Enter to select, digits to jump straight to an option, and the hint shown on screen. It is what makes it feel like a console menu rather than a web page.

A vocabulary, not a screen

The six decisions above are worth nothing if they only apply to the one screen you cared about. CircuitDojo has three menu screens: placement, home and the challenge brief, and the placement screen kept its original layout through two rounds of polish on the other two. It is the first screen anyone sees, so it was the one screen where being a version behind actually mattered.

The fix is to make the vocabulary shared code rather than a shared intention:

Exported from MenuShell.jsxWhat it settles
MenuShell + padLocked viewport and one of two safe areas, a calm field or an edge-hugging HUD
MenuOptionOne row anatomy: mono index, label, hint, meta. emphasis="primary" scales it for the one action a screen exists for
at(step)One entrance beat, so three screens cannot drift into three timings
Deleting the old component is the point

The row this replaced: oversized, with a rule that grew on hover: survived because it was still imported in one place. A design system with two row components does not have one row component; it has a migration you have not finished. Porting the last screen and deleting the old export are the same task, and if you cannot delete it you have not finished porting.

Containment: the rule that decides the layout

Decision 1: lock the viewport: is the one that bites. overflow-hidden does not make content fit; it makes content that does not fit unreachable. CircuitDojo's home screen learned this the expensive way. Six oversized rows in one vertical stack measured fine on the machine it was built on, and at 1366×640 the heading sat 48px above the top of the window while the last row fell 37px below the bottom, with no scrollbar to rescue either.

Two changes fix that class of bug for good.

Band the screen, and let the middle absorb the slack. Header and footer size to their content; the body takes what is left and is allowed to be small: 

<div className="flex min-h-0 flex-1 flex-col gap-...">
  <header className="shrink-0 ...">...</header>
  <main   className="grid min-h-0 flex-1 content-center ...">...</main>
  <footer className="shrink-0">...</footer>
</div>

min-h-0 is the load-bearing class. A flex child defaults to min-height: auto, which refuses to shrink below its content, so without it the middle band pushes the footer off the screen instead of giving way.

Clamp against both axes. A width-only clamp cannot see the case that actually breaks, which is a window that is wide but short: 

/* 5.4vw on a 1366×640 window is 74px of heading in 640px of height. */
fontSize: 'clamp(2rem, min(5.4vw, 8.5vh), 4.5rem)'

The min(vw, vh) inside the clamp means whichever axis is scarcer wins. Pair it with [@media(max-height:560px)]:hidden on genuinely optional lines: a tagline, a keyboard hint, and the screen degrades by dropping detail rather than by hiding what you came for.

One axis beats two columns

The challenge brief began as a two-column split: title and goal on the left, requirements on the right. It looked orderly and read badly. A split like that has no single entry point: you take in a heading, then jump sideways to find out what it actually asks of you, and the eye has to decide twice where to start.

A mission briefing in a game runs top to bottom on one centred spine: classification, title, objective, numbered requirements, how to begin. One reading order, no competition. Rebuilding the brief that way is a layout change with no styling in it at all: the same glass, the same type, the same colours, re-stacked.

MoveWhat it buys
Rule-flanked classification line above the titleLevel and topic read as a mission tag, not as metadata bolted to a corner

Narrow margins need a maximum width to work

"Hug the edges like a game HUD" and "keep the text readable" only coexist if you separate the two frames: the page padding comes in close, and the column inside it gets its own max-width. Chrome sits out at the edges, content stays on the centre line. Pulling the page padding in without capping the column just gives you 1900px-wide sentences.

Test the short window, not just the small one

Responsive testing is habitually about narrow phones. The window that breaks a locked-viewport layout is the laptop with a browser toolbar, a dock and a video call open: 1366 wide and 600 tall. Resize the height and watch what leaves the screen.

  transition-all duration-300 ease-smooth hover:border-zinc-900/20 focus-visible:border-zinc-900/20">

  {/* Leading rule: 0 → full on hover. The classic menu affordance. */}
  <span className="relative h-[2px] w-6 overflow-hidden rounded-full bg-zinc-900/15">
    <span className="absolute inset-y-0 left-0 w-0 bg-zinc-900 transition-all duration-300
      ease-smooth group-hover:w-full group-focus-visible:w-full" />
  </span>

  {/* Label nudges right: motion toward the action you are about to take. */}
  <span className="transition-transform duration-300 ease-smooth group-hover:translate-x-1">{label}</span>

  {/* Chevron fades and slides in only on hover: reward, not clutter. */}
  <svg className="-translate-x-1 opacity-0 transition-all duration-300 ease-smooth
    group-hover:translate-x-0 group-hover:opacity-100" />
</button>
The group pattern

Tailwind's group on a parent plus group-hover: on descendants lets one hover drive several coordinated changes. Three small movements that happen together read as one deliberate gesture, which is the whole difference between "a link" and "a menu item in a well-made game".

Why focus-visible is mirrored on every hover state

Keyboard users get the same affordance as mouse users, and focus-visible (rather than focus) means mouse clicks do not leave a focus ring behind. Accessibility and polish are the same edit here.

The full-bleed application layout

The workspace uses the opposite strategy from the menu, and for a reason:

// The canvas is the app; everything else floats above it.
<div className="relative h-full w-full overflow-hidden">
  <div className="absolute inset-0"><SchematicCanvas ... /></div>

  // Corner-anchored, pointer-events-none containers so the canvas stays clickable
  // everywhere the widgets are not.
  <div className="pointer-events-none absolute left-4 top-4 z-20 flex flex-col gap-3">
    {widgets.brief && <BriefWidget ... />}
  </div>
</div>
Why floating widgets instead of docked panels

A schematic wants every available pixel. Docked panels permanently subtract width from the subject; floating glass panels overlay it and can be dismissed to zero. The pointer-events-none wrapper with pointer-events-auto children is the trick that makes it work, gaps between widgets remain live canvas.

One element, one owner of transform

Hovering a menu option made it judder and flash an outline. Three separate defects were stacked on the same element, and only one of them was obvious.

CauseSymptomFix
An entrance keyframe and a hover lift both animating transform The lift applied, dropped or half-applied depending on where the entrance had got to Entrance moved to a wrapper element
focus() called on hover, to keep the keyboard cursor in sync The focus ring chased the pointer down the list Focus only follows the keyboard
transition-all Outline and shadow changes animated over 300ms instead of appearing Transition only the properties that should move

The first is the one worth remembering. A filled keyframe animation outranks a plain declaration, so an element carrying animate-* cannot also be styled with translate, scale or rotate: the animation wins, silently, and only sometimes. If an element needs both an entrance and a state change, they belong on different elements.

The highlight and the focus ring are not the same thing

A pointer highlight says "this is under your cursor". A focus ring says "this is where your keystrokes will go". Syncing them by calling focus() on hover conflates the two and produces a ring that follows the mouse, visual noise for the pointer user and a lie for the keyboard one. Track which device moved the cursor and only move focus for the keyboard.

Make the metaphor mean something

Three attempts needed a representation. A heart is the obvious one and the obvious one is usually a sticker: drop in a generic glyph, tint it red, done. That version would carry no information: it would be a counter wearing a costume.

The version that earns its place makes the metaphor literal. A life is a closed circuit: the heart is routed in straight runs and 45° mitres like every other trace in the app, with a via at each lobe, and a current packet running the loop. Losing one is what losing one actually looks like: the trace breaks at the bottom point, the charge drains out, and what remains is a dashed outline, which is already the schematic convention for something that is not really there.

StateWhat it drawsWhat it means electrically
AliveClosed loop, filled, current flowing, slow beatA complete circuit
BreakingSurge, arc across the gap, fill drains, settleThe moment it opens
LostDashed outline, open at the bottom, no fill or viasAn open circuit

Only one of those three is loud. The resting beat is 2.6s and the three hearts are deliberately out of phase, so they read as three circuits rather than one animation applied three times, and so the row can sit at the bottom of the screen for an hour without becoming something to ignore.

Put the animation where the eye already is

The lives sit against the button that spends them. The first version had them in the results panel, which arrives in the same frame as the loss, so the break played while the eye was being pulled to a panel expanding underneath it. An animation nobody is looking at is a wasted animation, and the fix is placement, not duration.

Let the drawing size the sheet

The reference answer is presented as an issued drawing: a double frame and a title block, because those say "this is the released version": exactly the status it has, and exactly what separates it from the learner's working sheet.

It also assembles itself. Parts fade in, then wires draw between them, then junction dots land: the order the circuit would actually be built in. The finished picture is the thing they have already failed to produce three times; the sequence is the part that carries new information. 

// Paint order and time order are independent. Wires are painted first so they
// pass under the symbol bodies, and animate last so the parts arrive first.
const ratio = Math.max(box.w / box.h, 0.62);  // the sheet takes the drawing's proportions

That last line fixed the thing that made it look cheap. A rail-to-ground ladder is about 1:3; stretched across a wide panel it letterboxed itself into a thin strip with acres of blank sheet either side, frame and title block floating far from the drawing. Sizing the sheet to the content puts the frame back on the edge of the drawing. The floor stops a very tall circuit becoming a ribbon: past that point it centres on a portrait sheet, exactly as it would on paper.

If it can fail, it must be able to look failed

A net label a few units off the wire renders identically to one sitting on it: same marker, same text, same colour. It is the only item on a schematic whose entire purpose can fail with no visible difference, and the checker then reported three separate topology problems, none of which was the actual fault, sending the learner to rewire a circuit that was already correct.

The fix is not better error text. It is that the state must be visible in the thing itself: an unattached label now draws in the unconnected colour, with the hollow square an EDA tool puts on a dangling end, captioned "not on a net". You can see it is broken without running anything.

Report the cause, not the symptoms

The three topology failures were all true and all useless. One root-cause error: "the BTN label is not touching a wire, so it names nothing": replaces them, and it is an electrical rule, not a requirement miss, because it is wrong regardless of what the brief asked for. When several checks fail together, ask whether one upstream fact explains all of them, and say that instead.

The rule it replaced warned whenever a label appeared only once: advice that was both wrong and actively harmful, since naming a node so the specification can refer to it is precisely what these briefs ask for. It told the learner their correct label connected nothing.

Where do you mark a thing that is not there?

Every failure above can be ringed where it is. One cannot: a part the brief requires and the sheet does not have. The mark belongs where the component isn't, and there is no such coordinate.

The instinct is to write a sentence about it and consider the job done. But a sentence in a results panel is the thing a learner has to translate back into an action, and translation is where people give up. So a missing part gets a standing chip of its own: outside the panel, surviving the panel being closed, and clicking it opens the parts search on the thing it is asking for.

The general rule

When you cannot point at the problem, point at the fix. An indicator that only describes a gap makes the reader do the work; one that opens the tool that closes the gap has done it.

One decision, two answers

Once a sheet is in progress the main menu has two lead actions: continue it, or start something new. They are not equals: continuing is what is nearly always wanted, and starting over throws away work.

OptionWhat it saysCost
Two full-width rowsThese are alternatives of equal weightA row of vertical space, and a false equivalence
One row, a menu behind itStarting new is an advanced actionHides something people do constantly
One primary-sized panel, split unevenlySame decision, two answers, one clearly the defaultNothing

The split keeps the primary's footprint exactly: continue takes the majority and the numbered badge, start-new takes the end at secondary weight. Each half stays its own <button> so the keyboard walk still visits both and the digit shortcuts stay in visual order.

The destructive half goes through a dialog, and the dialog's job is to name what is actually lost. "You will lose your progress" reads as "your account is being reset": it overstates, and warnings that overstate are the ones people learn to click through. "The circuit you have drawn is cleared. Your level, solved count and concept progress are all kept" is longer and infinitely more useful.

Interaction states are not optional

.btn {
  @apply transition-all duration-200 ease-smooth
    /* Pressed: a tiny scale-down is the cheapest "it responded" signal there is */
    active:scale-[0.97]
    /* Disabled: dim AND non-interactive, so hover does not lie */
    disabled:pointer-events-none disabled:opacity-35;
}

Every interactive element needs four looks: rest, hover, focus-visible, active. Plus disabled where it applies.

Accessibility, as design

  • Contrast. 4.5:1 for body text, 3:1 for large text. Your muted grey must still pass.
  • Focus visible. Never outline: none without a replacement.
  • Semantic elements. A clickable thing is a <button>; it gets keyboard and screen-reader behaviour for free.
  • Labels on icon buttons. title plus aria-label.
  • Hide decoration. aria-hidden="true" on ambient SVG so screen readers skip it.
  • Do not encode meaning in colour alone. This app pairs every status colour with a word and an icon.

How to develop taste

  1. Steal structure, not style. When a site impresses you, work out its type scale, spacing rhythm and how many colours it uses. Copy the system; invent the surface.
  2. Build the tokens first. Scale, spacing, radii, shadows, easing. Then compose only from those. Constraint produces coherence.
  3. One signature move per project. Here it is glass over a schematic sheet, with the iris wipe as the punctuation. One memorable idea beats five competing ones.
  4. Reduce. Take a finished screen and remove a border, a shadow, a colour, a label. Most survive. Whatever breaks was load-bearing.
  5. Look at it small and squinting. Blur your eyes: the hierarchy should still be obvious as shapes. If everything is one grey mush, your contrast of size and weight is too flat.
  6. Write the reason down. Comment your design decisions in the CSS the way you comment tricky logic. Future-you needs it just as much.

From plain to designed: a checklist

  1. Replace all font sizes with 5-6 clamp() steps.
  2. Tighten headline tracking to -0.02em...-0.035em.
  3. Snap every space to one 4px scale; delete the odd values.
  4. Reduce to one neutral ramp + one accent + three semantic hues.
  5. Swap pure black/white for #18181b / #fafafa.
  6. Give every surface one border, one faint shadow, one radius from the system.
  7. Add hover, focus-visible and active states to everything clickable.
  8. Pick one easing curve and one entrance animation; apply everywhere.
  9. Double the outer margins of your main layout. Then check it again.
  10. Add the prefers-reduced-motion block.
  11. Squint at it. Fix whatever no longer has hierarchy.
